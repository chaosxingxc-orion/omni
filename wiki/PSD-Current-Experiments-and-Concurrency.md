# 当前实验与推理并发选择

## 实验目的

先锁定可用的P→Slot→Decision模型配置，再开展TFRL。当前共同工作基线为P OFF、Slot ON、Decision ON。新增P thinking实验检验其是否改善候选理解与最终SLU，同时衡量额外解码成本。紧凑P与操作辨别P是独立提示实验，不与thinking变化混合归因。

全部复用既有Fold A1080及冻结知识。两路各4卡TP4，Qwen3-Omni-30B-A3B BF16，ctx65536、GPU/NPU memory allocation比例0.92，prefix cache和chunked prefill开启，CPU准备/校验8/8、音频缓存4GiB。真实服务启动命令已再次核对。

## 并发与流量优化计划

1. **先提高供给到96，再视实测到128。** 当前客户端64使引擎128容量没有吃满；KV约一半且无抢占支持试验价值。保持引擎与提示不变，复用已准备C96/C128配置。先验收已armed同OFF父C96；收益不能未经验证直接迁移到长输出的ON或P ON。
2. **同时观察吞吐与时延。** 合法样本/小时、全部样本平均/P95完成时延、P/Slot/D请求耗时、质量损伤和KV抢占共同评价。并发变大可能提高总吞吐但降低单序列解码速度；不得承诺1.5倍或2倍。已定C96工程目标为同父合法吞吐+10%，不是统计显著性阈值。
3. **流量分两层。** CPU提前产生ready请求，适当增加可推进轨迹数以覆盖节点交接间隙；model_inflight控制真正送入服务的请求。现有role_input_offload/ready_request已开。只有观测到HTTP供给掉谷再试“轨迹数高于在途请求数”，不盲增准备/校验线程。
4. **再考虑引擎参数。** 128确实有收益且KV、尾时延可控时，才通过独立配置试max_num_seqs192/256；仅提高客户端超过128可能只是加长服务队列。2048 token调度预算优先级低于客户端并发；prefill目前短，不能假定改4096/8192就加速长decode。变更引擎须在任务边界，不中断当前运行。
5. **减少无效解码和有害长输出。** 紧凑P/Slot候选已覆盖结构空白；Decision在完整覆盖OFF占请求时延约73%、输出约76%，值得质量受控优化。不能因成本直接关闭带来槽位收益的thinking。prefix已实际命中，固定前缀可复用，但要保持知识与任务信息完整。

30B-A3B每token激活约3B参数不意味着只需3B模型内存；30B权重、长上下文KV、多模态处理与TP通信仍有成本。4卡能否承载更多并发应由真实分布验证。当前证据支持增加客户端并发的探索，不足以证明某个kernel瓶颈或保证8卡持续80%以上Core。
