# 节点请求效率与工程优化

更新：2026-11-05；观测窗口 09:00:26–09:07:48 UTC。

## 结论

模型推理使用两个四卡NPU实例，prefix cache已经开启并生效。当前主要限制是应用侧请求准备和校验使引擎缺少持续输入；还没有达到可称为“8卡满载”的状态。先优化工程基座，当前实验继续运行；新版通过功能和效率验收后再切换并断点接续，暂不新增大规模实验。

## 推理过程与设备分工

CPU负责数据读取、知识选择、上下文组装、请求渲染、token计数/FIT调度、身份与预算检查、响应解析、结果校验和持久化。P、Slot、Decision的模型请求均发往NPU服务，模型执行配置为`device_config=npu`。音频解码、tokenization及请求调度等前后处理仍包含CPU工作；不能将模型使用NPU理解为整个业务流水线都在NPU执行。本次没有逐算子profiling。

同一样本保持P→Slot→Decision依赖，不同样本可以交错执行。A为P off→Slot off→Decision on，B为P off→Slot on→Decision on，均使用原Fold A1080；A/B名称为实验臂，均不是Fold B。统计节点请求数不能替代完成样本数或准确率。

## 慢在哪里

最近600秒已结束应用计时中，一次render均值A/B为38.81/37.25秒，一次session检查14.81/13.10秒，其中maps检查7.08/6.03秒。正常contact存在prepare、FIT、发送三次渲染，以及多次会话检查。模型adapter预算锁内包含会话校验，是已确认的串行路径；实际锁wait/hold尚未细分，不能把全部等待都归给它。

音频文件读取均值0.35/0.28秒，base64约0.0002秒；FIT容量等待约0.38秒/接近0。当前没有证据优先升级音频搬运缓存或盲增FIT容量。debug计时也有全局写锁，需测其开销，不能凭猜测归因GIL或磁盘。父子span重叠、跨样本并发，以上均值不能相加或直接相减推算一个样本的耗时。

此前不可变render缓存回放更慢，未合入。线程级连接与相同maps解析复用已合入main `a04646ed`，覆盖普通worker和pipeline路径；尚未部署到活实验，没有线上加速结论。

## 完整分析补充：响应后也有等待

只读分析已交付完整报告、复算脚本、来源清单和68条contact时间线；主线程校验208项、39份输入通过。对已结束的同一contact做区间匹配，transport之前平均A/B为164.95/140.72秒，返回之后到外层request结束仍为151.03/134.58秒。它们是已结束contact的墙钟跨度，不能称为纯校验CPU时间。

代码确认响应计数也重新获取同一`_metering_lock`，因此新请求在锁内进行慢身份校验时，响应线程也可能等待。尚未直接计量锁wait/hold，剩余时间还包含journal、trace、序列化与调度，不能将全部残差归给锁。工程实现必须同时检查发送前与返回后的同步路径，单独增加解析线程可能仍被该锁阻塞。

归档中197份请求的固定system/task instruction一致（8118字符），已有可共享前缀。当前音频位于知识之前，跨样本音频变化可能中断后续KV前缀复用；这是布局分析，未重建token序列，不能用字符前缀换算命中率。缓存已开启，但仍有待独立验证的布局优化空间。

## 用户确认的实施顺序

1. **输入提前准备**：固定模板、数据索引、媒体及知识不变量在启动准备阶段加载和验证，形成可复用、按内容身份失效的有界缓存。后续节点所需动态上游输出仅在依赖完成后组装，不能提前伪造完整请求。CPU预取与NPU执行重叠。
2. **提高实验侧并发**：准备线程、样本准入、模型在途请求和结果处理分别配置，以64/96/128为候选逐档验证实际吞吐，保持有界队列及背压。先解决慢校验所在临界区，再增加并发，防止仅增加CPU等待。两TP4和科学配置保持一致。
3. **多线程结果校验**：独立有界线程池处理可并行的响应解析、结果校验和整理；下游节点依赖所需校验仍要先完成。共享预算与checkpoint沿用原子/单写提交，不让多个线程无序追加同一状态文件。线程异常、取消及shutdown均可追踪和恢复。

三项进入同一固定Docker基座，外部配置选择workers、队列容量、并发与normal/debug模式，启动入口保持脚本化。纯Python校验不因使用线程便自动获得多核提速，须测真实收益。

## 验收与切换

功能验收先覆盖真实普通worker和pipeline分支、样本依赖、payload一致性、预算边界、异常/取消、背压与恢复不重复。效率验收使用原有真实数据，记录已完成/总样本、完整轨迹与拒绝、秒/样本、模型在途数、队列等待、各阶段墙钟、卡数和NPU空闲时间。不得用合成负载或局部函数加速冒充业务吞吐。

供给瓶颈解除后再评估`max-num-batched-tokens`从2048到4096/8192等单因素配置；prefix只能减少共享前缀的prefill，不能消除CPU检查和decode。提高共同前缀复用应保持固定指令前置、动态内容后置；若改变实际prompt顺序，必须独立评估精度，不能当作无影响性能补丁。

当前实验继续。新版验收后：停止旧版准入→等待在途请求完成→结算未知状态→保存检查点→替换镜像和配置→仅接续未完成样本。正常监控600秒或终态事件，不高频轮询。观察到无收益或效率退化时保留证据并回退，不预先承诺加速倍数。

## 真实请求离线 profile

使用旧 Fold A 配置和已保存的 P、Slot、Decision 各一条真实请求，旧源码与当前候选渲染出的模型body和projection receipt摘要一致。这仅验证三个请求的投影，不是完整新调度轨迹或NPU性能验收。

带cProfile的三次渲染累计25.893秒，`validate_slot_view_context`调用36次、累计26.517秒，`KnowledgeSnapshot.content_hash`调用43次、累计27.840秒；后两项也包含初始化，且区间嵌套，不能相加或用比例推算加速。调用链显示逐条证据投影重复验证同一完整知识快照，是已量化的CPU优化候选。后续需使用不可变的已验证上下文或等价方案，保留内容变化拒绝，比较无profiler及normal/debug真实负载；不能直接给可变对象加“已验证”标记后跳过检查。

第二版候选将一次渲染所需投影数据固定为私有不可变对象，减少逐条证据重复验证。同样三份真实请求的body与receipt摘要仍一致；带profiler的render累计降至6.985秒，相关31项固定镜像测试通过。第一版整份deepcopy消耗11.315秒，已调整；这些局部观测不代表业务吞吐倍数。该投影补丁已独立合入main（199c698a），未部署；三条输入已按文件摘要固定，无profiler对照和完整效率版本集成仍待验收。

## 工程实现验收进度

优先级固定为工程效率优化；新增大规模实验暂缓，当前两臂继续。统一镜像的外部配置、原1080条输入准备及启动入口已有验收材料；包含最新效率修改的最终镜像仍待构建验证，不能用打包成功代表流水线提速。

候选已实现准备/校验有界线程池、按contact释放并发名额、响应计数独立锁，以及会话检查移出预算临界区。此前固定镜像82项回归通过；后续取消处理另有19项相关测试与2项准备/校验重复取消测试通过。各测试对应不同源码阶段，不合并宣传为最终版全通过。

初版独立准备池只处理role-input，取得contact名额后仍执行request prepare和FIT，未达到用户要求。新候选开始将prepare/FIT移到发送许可之前，相关固定镜像9项测试通过；仍须覆盖准备异常、等待许可时取消、fallback二次准备和实际payload一致性，尚未验收。`model_inflight`不能直接解释成纯HTTP在途数，发送前仍有身份/数据校验。64/96/128配置还须匹配deployment admitted level。

独立审查发现ready候选在准备/FIT后失败或取消时，未发送对象会留到client关闭才清理，两条取消路径缺少联系级终态处置；主线程已复现并交原开发者修复。现有FIT持久记录未见删除，不能将未发送请求算为unknown。ready模式尚未验收，不能随已合入的投影补丁直接启用。

旧实验来源分析已完成：两臂真实源码、配置和归档checkpoint哈希链已核验，交付材料完整性独立复核通过。仍有部分知识资产内容证据、最终集成源码和兼容桥预检待完成。运行中归档不是事务一致恢复点，来源核验不等于可切换；当前未停止旧实验，也未执行新版resume。

节点耗时工具已完成Slot、失败终态分母、逐样本明细及异常逐行隔离，相关28项测试在固定镜像通过。正式checkpoint reader和CLI覆盖已有A297条/B226条归档；主线程独立核对源码与测试输入、容器退出及逐行聚合后合入main。两份归档分别含195/118条完整链候选、99/104条拒绝、3/4条其他终态；完整链不代表正确答案。样本边界缺进程身份，相对节点的残差仍明确标为同一单调时钟假设。该工具不产生新的精度结论。最终效率验收将以真实数据完成数、秒/条、队列等待、实际在途数与资源利用为准。
