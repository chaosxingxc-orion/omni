# 节点请求效率与优化计划

## 已验证结论

对固定Fold A1080三节点运行的一次只读快照进行离线审计，共3764条已结束计时记录；源码、归档、37份生成响应和42份FIT记录均有哈希校验。结果是工程诊断，尚未实施性能干预，也没有已验证的加速倍数。

正常请求在prepare、FIT、transport三个阶段重复渲染。首次模型身份校验读取约63.45GB，耗时88.86秒，但后续已命中缓存，不能当作逐请求成本。prepared校验69.84秒同样是启动成本。容器启动至首个实际HTTP区间约337.45秒；其中仍有未细分的初始化。

一个完整请求的三次render分别约4.97、6.50、4.90秒；三次音频读取总计仅约0.006秒。全快照base64编码累计约0.028秒，因此没有证据优先把瓶颈归于音频搬运或编码。后段session/maps检查显著变慢，但未做CPU profile，不能直接归因GIL、磁盘或核数不足。

## 优先实施

|顺序|工程修改|验收条件|
|---|---|---|
|1|配置化复用不可变渲染材料|真实prepare→FIT→发送减少重复工作，HTTP字节和receipt一致；默认兼容|
|2|细分预算锁及session/maps耗时|先测wait/hold和CPU时间，再缩短临界区；并发预算和唯一请求仍正确|
|3|显式准备FIT首次factory|避免初始化与contact claim共用锁造成队首等待；不重复调用端点|
|4|改进终态事件接续|精确进程终态触发结算，结算事件直接唤醒后继，避免多个600秒等待串联|

渲染复用已交独立工程进程实施。缓存必须绑定payload、媒体内容、配置、模板、projection及transport实例，不能共享可变dict。prepare的占位request_id在正式发送前会变更，必须正确重绑来源，不能用仅sample_id的缓存制造跨请求混用。每次发送仍保留活会话、租约、预算、一次性授权和journal校验；fallback或compaction变化需重新验证。

## 实验与工程并行

当前两臂仍在既有Fold A1080上比较P off→Slot off/on→Decision on。冻结运行树不热改。CPU优化先在固定镜像做真实路径回归和离线性能测量，证实收益后，以新版配置安排接续，不以重复无收益实验填满队列。

意图候选归组另行分析：同intent_id、证据及不确定字段相同而解释措辞不同，现行整对象去重会拒绝。拟评估按意图归组、保留证据与不确定性的程序策略；它属于模型协议与知识消费方案变更，需独立版本同折验证，不能当作不影响结果的纯性能补丁。

依赖顺序为：当前两臂封存与配对评分→Fold A节点定向修复/验证→候选冻结→原Fold B1080确认→完整TEST13078→TFRL。工程开发、离线错误分析和后继配置准备同时推进，不新增开发集。

## 可复用约束

计时必须区分墙钟、CPU时间、父子嵌套和跨样本并发，禁止累加所有span作为实验时长。完成口径分为终态样本、完整三节点轨迹及官方正确性；拒绝样本保留在评测分母。当前记录不足以推算稳定ETA或证明8卡满载。

固定镜像和源码只读；启动与预检均配置禁止生成字节码，避免污染封存评分源码。日常观察约600秒，明确终态用事件唤醒；事件只是通知，不能代替逐请求结算。SSH中断不重提未知请求，轨迹与费用持续落本地盘并异步归档。
