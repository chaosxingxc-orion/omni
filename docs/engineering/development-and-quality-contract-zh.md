# 功能基线与非功能质量工程规范

状态：依据用户最新约定生效；作为本项目及后续工程的复用规范。本文规定开发顺序与验收方式，不代表所有条目已实现。

## 一、开发顺序

先交付完整的最小业务功能闭环，为关键行为增加测试并锁定特性基线；随后集中优化可用性、可靠性、稳定性、性能及可观测性。按可独立验收的业务增量推进，不必等待全部远期功能完成才处理质量问题，也不为追求理想工程基座长期推迟业务功能。

每项工作登记：业务目标、功能或非功能分类、输入输出契约、验收用例、前置依赖、基线版本、实测结果。功能开发回答“系统能否完成预定任务”；非功能开发回答“在规定负载和故障条件下能否持续、正确、高效地完成任务”。

贯穿两类工作的最低正确性约束：数据与策略身份一致、训练/评估边界明确、奖励可追溯、已花成本不丢失、未知请求不盲重发。这些约束保护实验结论，不是额外人工审批。发现数据损坏、重复执行或错误计分，应立即修复；吞吐、缓存、日志深度等优化，先量化影响再排序。

## 二、功能基线如何锁定

每个特性至少定义一个成功用例及其关键边界/失败用例。对决定业务正确性的行为做测试，避免只复制实现细节。复杂闭环需要共享正式入口的集成用例，再以固定真实数据做有限运行验收；替身通过不等于真实推理已通过。

本项目的特性矩阵：

| 特性 | 必须锁定的行为 |
| --- | --- |
| 多模态推理与评分 | 同一输入、原始输出和实际被评分答案可关联；意图及槽位沿用官方语义 |
| 轨迹采集 | 保存感知、检索、决策、工具输入输出、策略版本、奖励和成本；无相关阶段时显式标记 |
| TFRL 更新 | 正确区分有差异和同分组；所有更新绑定真实来源；不把部分正确答案当成功示范 |
| 知识构建与消费 | 规则有范围、触发条件和支持依据；冻结候选内容、渲染与顺序后评估 |
| 分片与融合 | 全组覆盖、无遗漏或重复；跨片冲突有处置；中间产物不能冒充最终候选 |
| 版本晋升与回退 | 配对评分决定保留/拒绝；下一轮使用实际采用版本采轨迹，保留父子关系 |

锁定件包括：提交、测试命令和结果、数据/配置/模型版本、输入输出契约与真实验收证据。后续非功能优化必须通过这些用例；需要改变业务语义时建立新特性版本，不能把它混入性能补丁。

## 三、可复用的非功能要求

| 质量属性 | 约束与实现原则 | 验收证据 |
| --- | --- | --- |
| 可用性 | 服务与任务脱离交互连接；任务持久排队；终态驱动后继；CPU准备/评分/分析与加速器执行异步 | 断开SSH后继续运行；后继自动接续；分别统计服务可用时长和有用任务供给空档 |
| 可靠性 | 原始响应和断点持久化；唯一运行身份与互斥；已知结果复用，未知请求先核验 | 注入发送前、响应落盘后、封存前故障；无重复已知调用、无丢失响应、账本一致 |
| 稳定性 | 队列有界、资源有限额和背压；故障隔离；变更能回退 | 连续多任务交接、内存/句柄/队列长度趋势及失败率；明确负载与观察时长 |
| 实验效率 | 以有用完成量和时间到结果为目标；CPU不阻塞无依赖的推理；有明确高收益优化时优先实施再续推 | 固定真实名单与完整配置，报告墙钟秒/条、尾延迟、任务空档和卡时 |
| 资源利用 | 对全部分配设备统计有效负载；有兼容任务积压时持续供给；不以无价值重复任务制造满载 | 每卡利用率、实例在途/排队量、有效token吞吐、可运行队列深度及饥饿时长 |
| 可观测性 | normal提供低成本进度/故障/成本；debug提供逐阶段细粒度事件；两者配置独立且版本化 | 能关联任务、样本、请求；分开排队、预处理、推理和持久化；量化debug开销 |
| 可复现与数据完整性 | 固定真实数据共享；配置及来源可验证；训练/开发/测试用途明确；结果原位更新且历史保留 | 名单摘要、完整配置、官方评分、完整成本和可核验归档；恢复演练 |
| 可维护与兼容 | 复用共享运行时、加载器、评分器；新接口保留明确兼容边界；优化可单独关闭 | 新旧路径回归；独立变更及回退说明；不修改运行中的绑定执行树 |

表中没有实测依据的数值目标，标记为待定；不得虚构已达到的SLO。具体项目为每项填入测量窗口、负载、阈值及负责人。不能用“服务进程存活”代替“实验有进展”，不能用峰值利用率代替长期有效吞吐。

## 四、优化与报告纪律

一次优化明确瓶颈、假设、变更和成功条件，复用同一真实工作负载比较。吞吐秒/条与单条延迟分开；嵌套、并发耗时不相加。超出功能基线的缓存、并发或推理配置变化，记录完整配置后再实验。已有明确效率收益证据时，安全停派、保全在途响应、优化并断点接续。

进度统一报告：已处理/总规模、墙钟秒/条、卡数/实例数、剩余量/ETA、调用与tokens、未知请求数。未启动或缺少稳定速率时ETA写未知。常规监测采用事件或约600秒轮询，避免监测自身消耗过多资源。

结果进入GitHub Wiki原位维护，代码与规范及时同步main。对外记录结果和证据链接，原始音频、轨迹、凭据及内部地址不进入公开仓。

## 五、迁移到其他工程

复用上述工作顺序、特性验收矩阵、质量属性表和优化报告模板。主机名、卡数、固定镜像、模型上下文长度及存储路径属于本项目部署参数，迁移时替换；不把特定部署细节误当通用规范。

## 六、配置化开发与执行基线

实验差异进入版本化配置，启动与交接复用[固定脚本](configured-job-launch-zh.md)。执行器负责可复用的目录预检、身份绑定、后台启动、幂等状态和终态交接；业务入口负责数据、预算、评分及原生恢复。不得为每次实验重新编写启动器。先以真实任务和针对性用例锁定此功能基线，再集中改进队列效率、恢复和可观测性。执行器修改必须说明具体缺陷和验收结果，不能把配置填充称为代码优化。

## 七、持续同步入口命名

持续更新的状态页、计划页和同步目标使用不带日期的稳定路径：Wiki为 `Research-Status`，主仓说明为 `Research-Status-and-Plan.md`。日期放在正文更新时间、实验记录和Git提交中；独立历史实验结果可保留日期。状态原位更新，不每天创建新入口。旧日期页面仅保留迁移指引，不再作为同步写入目标。
