# Codex 子进程并行执行

## 执行方式

研发并行统一由主线程驱动本机 Codex 子进程，停用 collaboration 子智能体派发与通信接口。既有正常执行的子进程继续运行，不为切换方式重复启动实验。最多三个工作进程，禁止嵌套派发；主线程负责资源分配、验收、集成和与用户交流。

模型路由保持：Terra 负责工程、配置、测试和文档；Sol 负责样本、统计及错误根因；Astra 负责规划、评价和重新规划。Terra 确认连接失败后可按既有授权回退到已验证可执行的 Sol，记录实际请求模型及失败依据。

## 文件交接

每个任务使用固定目录，包含：

- `TASK.md`：目标、输入路径、修改范围、资源归属、依赖和验收条件。
- `cli-launch.json`：PID、boot ID、进程启动标识、请求模型、任务 SHA 与实际启动参数。
- `receipt.json`：子进程确认读取的任务 SHA 与真实接单时间。
- `cli-events.jsonl`、stderr 日志：保留执行和失败证据。
- `REPORT.md`、`result.json`：方法、实际结果、来源摘要、测试、成本、未完成项与续跑入口。

主线程将任务文件经标准输入交给 `codex exec`；恢复已有会话使用 `codex exec resume`，先确认原进程终态及后台业务归属。启动脱离交互 SSH，日志持续落盘。历史目录名称可保留，不代表继续使用子智能体接口。

## 调度与验收

启动后核对一次任务回执和实际业务动作。日常检查以终态事件或约600秒节奏进行；没有消息先读文件，没有报告先查进程与执行日志。PID 存在不等于原进程仍在，须结合 boot ID 和启动标识核对。退出码、规则确认或容器 running 均不能替代业务验收。

两条 NPU 队列各有唯一执行负责人；Astra 提前补充冻结来源、资源绑定及依赖明确的候选任务。研究规格、已准备、已准入、已入队、实际生成分开记录。无科学反馈依赖的 NPU 后继在资源释放后接续，CPU 评分与分析异步。未知请求不自动重发，断点、互斥和失败成本保留。

交付不完整时回到同一任务文件补充；主线程审核产物和决定性证据，不用口头确认替代实现。公开仓与 Wiki 只同步脱敏结论，私有轨迹和凭据留在原有证据目录。

## 执行中的文件增量

文件写入本身不会唤醒正在执行的 Codex 会话。主线程更新任务或审查意见后，工作进程须在修改前、测试后、冻结配置前和启动前读取对应任务文件及 `ROOT-REVIEW.md`，并在回执记录实际文件 SHA、读取时间、采用或未采用的意见及原因。仅记录初次接单不能证明后来约束已经送达。

涉及当前启动正确性的增量若尚未获读取回执，主线程先核验 CLI 的 boot ID、PID、start ticks 与进程组，再中断本机 CLI；确认其终态后，以同一会话 `resume` 并通过标准输入提供增量任务。不得同时启动第二个同会话进程。远端已脱离 SSH 的任务继续存在，恢复者先检查原容器/队列身份，再接续观察；本机通信中断不授权重复提交远端任务。

每次交付必须同时更新机器可读结果与报告。已发生的调用不能仍写 `generation_requests_new=0`；部分轨迹、官方评分、任务终态及资源租约结算分别记录。审查发现遗漏真实调用路径时，原工程负责人补实现和回归，主线程不以 helper 单测通过替代端到端路径验证。
