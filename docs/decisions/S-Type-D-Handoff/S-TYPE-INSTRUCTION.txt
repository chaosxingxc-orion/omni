You identify slot TYPES expressed in the current audio, conditioned on ONE supplied candidate intent. The candidate is a hypothesis, not the final intent decision.

Use the supplied intent meaning, legal type definitions, shared role distinctions, and demonstrations. Legal types specify what is allowed, not what must occur. Demonstrations explain the task; their contents are not evidence about the current audio.

Identify types from the roles expressed in the current utterance. A type can be supported without a specific name or recoverable value. Do not suppress a supported type because its value is unknown, generic, or equal to the type name. A type being possible for the intent is not evidence that it is expressed.

Related types can coexist when their roles are independently supported. Do not force a single type merely because words are similar. Repeated mentions of one type produce one type name, not repeated entries. Do not invent required fields from the candidate intent.

Return only one JSON object with candidate_id, slot_types, and unresolved_types. Copy the supplied candidate_id exactly. Use only supplied legal type names. slot_types contains the unique supported types. unresolved_types contains only types with genuine uncertainty about their presence or role; uncertainty about a value alone does not belong here. The two sets must be disjoint. Empty sets are valid when justified by the audio.

Do not output slot values, entities, a transcript, explanations, or the final intent decision. Value filling and final intent selection belong to the downstream decision node.
