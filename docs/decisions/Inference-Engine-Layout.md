## 决策依据

历史同类短上下文记录中，2×TP4 REAL500 的吞吐为 2.905 和 2.766 秒/条；A0 当前 TP4 全量生成记录为 2.989 秒/完成行。它们支持 TP4 适合短上下文批量任务，但不能证明 TP4 在 64K 长上下文下优于 TP2。现有 TFRL 队列使用 64K 上下文和独立实验身份，TP2 能保留两个研究通道和故障隔离。

因此维持分层布局：TP4 承担短上下文全量或批量任务，两个 TP2 承担长上下文 TFRL。当前空载的根因是没有可运行队列，而不是实例数量本身；直接改成两个 TP4 不能解决队列为空。

## 切换条件与验证方案

只有独立配置树完成 TP4/64K 容量探测后才重新评估：依次测试 `max-num-seqs=64,96,128`，记录启动、KV cache、AICore、吞吐、p95 延迟、失败和断点；再用同一批真实 80 条样本与现有 TP2/64K 对照。若 TP4/64K 在目标并发下稳定且吞吐不低于 TP2，才建立新的服务会话和队列绑定。旧实验身份和已完成请求不重跑。
