# 知识库最小集与开发反馈回补规则

## 要解决的问题

4451只是历史压缩版本，不是必须保留的底座。优化目标是在固定TopK相似问检索中，减少重复、竞争和不稳定代表，让正确标签稳定进入供给；条数减少本身不算业务收益。

## 两个阶段，使用不同的保留条件

**先找最小启动集。** 不要求保住4451库的每个已有命中，否则容易被历史成员绑住。只保留有真实TRAIN支持的类别和来源隔离后必要的可用性，尽量删掉其他代表。现已得到59条、覆盖59个有TRAIN支持的类别，达到当前类别/来源约束的数量下界；不表示59条足以覆盖每类全部表达。

**再按固定DEV回补。** 使用原624、1079、FoldA1080，定位漏召的具体表达及其与竞争标签的距离。从全域合格真实TRAIN中挑少量能修复这些错误的代表，排除全部DEV来源闭包。DEV只提供反馈，不复制其问题进库，不合成相同测试问句。

## 每次回补必须做什么

1. 在当前库上重新计算候选的修复及竞争风险，不能沿用上轮排序直接全部加入。
2. 整体评价新增、替换或少增多删后的实际检索，分别检查Q15/Q50问句与描述D5并集的完整命中向量。
3. 接受零回退且修复Q15漏召的候选，或零回退且比当前库严格更小的候选；同大小、同命中的换人不算进展。
4. 回补后再次逆删所有成员，包括新代表。保留每个成员不可删的证据，以及仍可由联合替换解决的缺口。

当前有限搜索每轮最多新增2条、删除2条，最多600个不同库状态；全域候选profile的计算另计。最终选优先比较召回修复、再比较条数，不保证找出所有可行小库。预算耗尽、单删失败都不能宣布全局最优。每轮应报告接受库大小、逐例修退、每类覆盖、TopK标签多样性、被拒原因和完整成本。

所有DEV已参与适应性优化；TEST未参与选择。只有独立测试确认后才能讨论泛化。召回覆盖也不等于P最终Top3，需要分开验收。

## 预算修正的历史结果

先用现有预算配置限制单个候选的补偿展开，让安全收益能够在预算耗尽前提交。每次接纳后，用新库重新计算全域TRAIN候选的修复、竞争和覆盖，而非一次加入上一轮所有安全候选。配置上界已核实：每轮最多96预筛＋96新补偿＋2诊断状态，三轮最多582；全域候选profile另记成本。缓存复用不消耗新状态额度，因此上限1不等于路径只有一步。本次实际576态完成三轮，每轮接纳1条；这不保证未来每轮都能获得收益。

每个改变后的库再独立逆删，并允许能替代旧代表职责的联合替换。若缩库损失某类表达，则从真实TRAIN寻找少量更有代表性的样本补回，再检查是否能替代更多旧样本。停止条件是有限搜索未发现满足覆盖和稳定条件的改进，不是到达某个预设条数。

## 最小化与回补的顺序

初始最小化只守真实类别覆盖、来源可用性和数据合法性，不以4451的全部开发命中为必须保持的约束；否则无法执行“先删到最小起点”。59只是在当前59个有合格TRAIN支持类别下达到数量下界。回补阶段用固定DEV定位表达覆盖缺口，添加或替换少量真实TRAIN，并再次逆删；没有“增长后不许再删”的成员。

对“一条替换两条”直接核最终库与完整父库的四组命中，不能要求每个中间删除都安全，也不能把各自单删的损失简单合并成联合职责。相同命中下优先较小库；收益与条数的非支配候选分别报告，避免只报告增益最大者而隐藏可行缩库。任何有限预算下的停止都只称当前搜索结果，不称已证明全局最小。
