# P 节点正式训练启动串验

资源已重新授予，八卡训练和两套 TP4 推理沿原控制器从 Clock 3 接续。两套实例均通过真实请求探针和缓存回执核验。以下无卡串验数据来自资源重授前，正式模型请求与优化器更新按各自账本统计。

恢复时的 DEV 启动故障有三处。外层容器的只读源码挂载遮住了部署引用的 SSH 文件，退出对账也导入了同名旧模块。评测子容器随后读到了只供历史校验的账本实现，启动入口和调度器构造器先后在导入历史费用时失败。完整 Docker 退出回执还超过了 SSH 的单参数长度限制。部署补齐同摘要 SSH，退出对账明确选择自动调度模块并通过标准输入传输回执。启动入口和调度器使用同一份封存的活动账本实现，容器只读挂载当前历史清单。

在隔离网络的固定镜像中，用实际启动参数串过两处历史费用导入和 DEV 初始化。两处账本均读回 **3,426 笔**，成本单位 **3,426**，未知 **0**。DEV 初始化读入 **8,690/8,690** 条，耗时 **7.74 秒**，业务发单 **0**。失败窗口保留原启动记录、期限、预算和容器身份，结清时核对远端原 guard、退出回执及账本中的确切新增请求数。

| 环节 | 本次实测 | 耗时 |
| --- | --- | ---: |
| 恢复入口 | 并行读取两台主机的卡占用、原容器状态与源码摘要；两台机器的 16 张卡当时均被占用 | 5.5 秒 |
| 原控制器 → DATA | 用原 DEV 请求沿原邮箱、传输和 DATA 入口走到执行前；源码检查、恢复绑定与配置校验通过。另验下一轮 DEV 选择同一缓存，保留自己的策略；TRAIN 不绑定该缓存 | 7.4 秒 |
| 评测容器启动 | 正式 Docker 参数经压缩后约 1.10 MB，低于现场 2 MiB 上限；同一镜像初始化 8,690 条真实记录，隔离线上租约和网络 | 8.0 秒 |
| DEV 输入实际读回 | 用活动策略配置读完 8,690 条特征和召回：129 条原封闭、1,989 条同录音复用、6,572 条已封闭的批量特征；每类各抽一条，组装 1 个 P 和 10 个 S1 请求包 | 109.0 秒 |
| TRAIN 首组组装 | 冻结的 2,949 条样本用正式加载器读取；首组 32 条用原采样与捕获入口装配 | 9.5 秒 |
| 训练续接合同 | 用原 `check_only` 入口读回 Clock 3 checkpoint、核对八个 rank 和源码。正式模板为 FSDP8、Docker 内存 1280 GiB | 0.19 秒（入口内部计时） |

这些秒数来自独立的阶段检查，不能相加当作训练启动的实测总时延。镜像冷启动、实际 DEV 推理、首组新轨迹、模型权重加载和首次优化器更新尚无本次墙钟数据。

这次修复了四类只有在实际交接时才暴露的问题：挂起的 DATA 配置先做恢复绑定再校验，保留原请求和预算；正式评测子容器按活动配置挂载策略回执；历史源码引用与本次活动源码按已锁定的源码契约分开；TRAIN 的执行器改写不进入官方 DEV 容器。容器可读、输入摘要和实际初始化现在都有独立证据。旧 CPU 编码窗口无执行、无费用、无未知请求，恢复时按原锁结清零执行预留；随后直接读用已封闭 DEV 缓存。

资源交接后，用唯一恢复入口沿原控制器继续。两套 TP4 从当次启动回执绑定策略、精度和缓存，然后完成 Clock 3 的完整 DEV 基线；随后用正式策略采集 TRAIN 新轨迹、封闭输入、提交八卡优化器并验证新 LoRA 的导出、切换及训推一致性。前三个正式全局 loss 和各自 checkpoint 到齐后只结束观察器，训练继续。完整 DEV 是当前正式配置中首个训练提交前的关键路径。后续 DEV 的缓存选择已在 CPU 验过，线上跨窗口接续仍待实测。
