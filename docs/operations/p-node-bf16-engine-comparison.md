# 同权重 LoRA 推理性能对照

### 真实录音首次进入实例：并发与 LoRA 精度（11 月 22 日）

同机两组 TP4、引擎并发上限 8，两个独立面板各 32 段真实录音，每段对每个引擎只请求一次。第一组客户端从 8 改为 12，平均排队 4.16 → 23.64 秒，整段 decode 31.82 → 32.71 秒，吞吐 0.167 → 0.168 条/秒；第二组交换卡组，8 对 16，排队 6.28 → 41.05 秒，decode 27.44 → 32.28 秒，吞吐 0.173 → 0.171 条/秒。各臂多模态缓存命中 0/32。这些终端计时含其他请求的调度，不能当成某个 NPU 算子的执行时间。

原生 vLLM‑Ascend 对照读取 step‑3 的相同发布件，SHA‑256 为 `56413c26a9ba62c1474081942cf2e4f64f772679a7ee9ff46eff2bb148b24e44`。从实际挂载文件读取 safetensors 头：384/384 张量为 BF16，共 6,684,672 个元素，文件 13,420,384 字节。训练的 FP32 主参数供优化器更新及恢复；HF 的 LoRA 前向使用 BF16 autocast。当前推理启动器指定的 FP32 是运行时 adapter 缓冲及算术路径选择；已对齐的 Q/K/V/O LoRA A 矩阵乘使用 grouped BF16。原生 CLI 对 float32 的启动拒绝发生在解析参数时，不是拒绝了发布权重，也不要求更换训练 checkpoint。把训练主参数改成 BF16 不会改变这份文件的类型或自动换掉运行时内核。参见 [LoRA 对齐记录](partner-handoff/lora-parity-playbook.md)。

### 首 token 后的单请求 decode：逐层与算子

在空闲实例各发送一条未用于此轮预热和计时的新录音，仅开启流式回传；收到首个非空输出后开启两步 profiler，其间没有其他请求。两端 4,496 个输入 token、11 个输出 token、相同排名、正常 stop。每个 rank 都观测到两遍完整的 48 层语言解码器。原生首层 RMSNorm 为 [1,2048]，attention 的 Q 为 [1,8,128]；当前实现 attention 的 Q 为 [128,8,128]，单请求的一行也走了填充计算。此处 128 是算子的行数，不是 128 条录音。

| 两步 decode，每卡累计设备计算时间，四卡中位数（ms） | 原生 | 当前 |
|---|---:|---:|
| 所有 compute task | 28.22 | 136.01 |
| Slice | 0.38 | 55.71 |
| GroupedMatmul | 4.55 | 31.19 |
| FusedInferAttentionScore | 2.71 | 6.53 |

rank 0 两步内 Slice 调用 192 → 582，GroupedMatmul 调用 192 → 1,056。单这两类就解释本窗口计算核累计时间差的约 76%；GroupedMatmul 包含多条业务分支，不能全部计入 LoRA。原生和定制的 Slice 输入也不同：定制首层记录中出现大 KV 张量 [5456,256,128] 的切片。该形状不等于实际搬运的字节数。优先用原生分页 KV、单行 attention 和原生投影作为单因素参照。单请求 trace 不代表 C8 时间线，不能据此把 29 秒按算子分摊；四卡时间不相加、累计核时间不等于用户墙钟时间。

[全窗口逐算子 CSV](engine-profile-bf16/window-operator.csv) 保留两组各四个 rank 的实际计算任务；[逐层逐算子 CSV](engine-profile-bf16/layer-operator.csv) 只列用宿主线程调用边界与实际设备 connection ID 唯一关联的任务。不用相邻层开始时间伪造 host 结束时间。定制 decode rank 0 有 10,482/12,056 个计算任务未能唯一映射到语言层；它们仍计入全窗口表。两次 prefill 遍历与纯 decode 分列。HCCL 和 CPU 调度均未作为计算核计入；没有观测到的融合内部边界不作推断。

### 业务筛样路径上的复测与 KV 读页实验

在组包、HTTP、解析和 SQLite 写账的实际路径上，用两套 TP4 分别处理同一组 32 条不同的新录音（每实例并发 8，累计输入 157,415 token）。原生请求显式指定 step‑3 adapter 的 alias，核对响应的模型名，再消费排名。两台实例上多模态缓存均为 0/32，前缀命中均为 67,456/157,415。结果来自隔离实验账本。

### 为什么训练保留 FP32 主参数

实际 step‑3 发布件中 384/384 个 LoRA 张量为 BF16。训练前向用 BF16，优化器更新、恢复用 FP32 主参数。原生运行时以 BF16 加载同一 adapter。定制服务声明的 FP32 adapter 缓冲是推理实现自己的选择；它不意味着所有 LoRA 乘法都用 FP32，48 层 Q/K/V/O 的 LoRA A 已使用分组 BF16 矩阵乘。

对 step‑3 配置指定恢复的 step‑2 提交和相邻的 step‑3 提交，按摘要核对 8 卡两份完整主参数。对每个元素取本次实际更新量 Δ = 新 FP32 值 − 旧 FP32 值，测量从 BF16 旧值加同一 Δ 并按通常规则舍入回 BF16 后，有多少元素仍等于起始 BF16 值。所有计算在 CPU 上离线完成。

| LoRA 矩阵 | 参数数 | FP32 值实际有变 | 从 BF16 主参数出发，本步写回无变化 | 占实际有变元素 |
|---|---:|---:|---:|---:|
| A | 3,932,160 | 3,932,117 | 3,330,858 | 84.71% |
| B | 2,752,512 | 2,752,512 | 7,728 | 0.28% |

这是单步固定更新量的舍入反事实；没有重算梯度、优化器或长期 reward。现有 FP32 主参数允许小更新在多步间累积；正式训练不改恢复格式。按同样方式运行 `audit_master_rounding.py TRAIN.local.json <更新后的封闭 checkpoint 目录>` 可复核。

### 减少 MoE 跨卡通信后的实测

对照以 tile512 为父版，只改专家加权求和的位置。父版先跨卡合并 8 个 BF16 专家槽再加权求和；候选保留 BF16 乘积，每卡对自己拥有的槽以 FP32 求和，再跨卡加并转回 BF16。每层每个 token 的该次归约从 8×2048 个 BF16 变为 2048 个 FP32，逻辑通信字节为原来的 1/4。加法次序随之变化。

两套 TP4、并发 8、16 条独立预热、32 条新的 RL 录音：候选/原生分段图的排队 2.819/0.849s，prefill 3.644/0.892s，首 token 7.752/2.116s，decode **11.941/2.599s**，HTTP 19.707/4.725s，吞吐 0.393/1.653 条/秒。两端都生成 362 个 token，32 个 stop，28 条可解析，P@3 命中 28/32；prefix 均 67,456/158,095，MM 均 0/32。330 个后续 token 间隔里候选有 221 个超过 1 秒，原生为 0。两份独立面板不能量出相对 tile512 的单因素耗时增量，但该候选没有达到工程参照的时延。5 条独立 HF 诊断串行全部成功，47 个共同动作中 16 个差值超 0.01，最大 0.25426；3 条完整相同序列的整段差为 0.18573、0.53169、0.53169。未观测独立 top‑1。该候选不晋级。

下一项对照单独从 tile512 派生，保持投影、MoE 和缓存写入路径，将 48 层语言注意力的 FIA 调用恢复为同镜像原生实现（所有 attention 阶段），核对实际后端源码摘要。两臂测试不启用 profiler。

### 逐迭代对账：单条 decode 为什么明显超过短回复的纯 decode 时间

从 tile512 单独开启原生逐迭代日志。16 段不同录音预热之后，另 32 段 RL 录音持续并发 8，每端每段只发一次。候选与原生平均 decode 12.202 / 2.867 秒，首 token 6.710 / 2.028 秒，HTTP 18.925 / 4.906 秒；均 32/32 正常结束。独立五条 HF 诊断共 50 个共同动作及 4 个完整序列概率差全零，无独立 top‑1。该诊断版本不替换工程基线。

| 引擎步骤类别 | 步数 | 同步生成的后续 token 数 | 步时中位数 / P95 | 按生成 token 数加权的等待 |
|---|---:|---:|---:|---:|
| 纯 decode | 23 | 101 | 113 / 1,678 ms | 38.52 请求秒 |
| prefill 与 decode 同步 | 47 | 243 | 1,515 / 1,630 ms | 351.31 请求秒 |
| 纯 prefill | 3 | 0 | 1,178 / 1,277 ms | 0 请求秒 |

73 个连续引擎步骤覆盖全部 344 个后续 token。令单步等待时间乘以该步生成 token 数，再按表中类别求和：合计 389.84 请求秒；累计实际相邻输出间隔 390.46 请求秒。混合步约占实际累计间隔的 90.0%；引擎计时含执行结果等待及必要的采样，不是设备净算时。混合步处理了 85,573 个上下文 token。纯 decode 中也有两步超过 1 秒（批内 8 / 4 个生成请求，2.715 / 1.678 秒），其具体原因未确认；不能将这些长尾都归到 prefill。该结果说明多个输出确实同一步生成，但也一起等待新请求的长上下文计算，不能用纯 decode 的中位步时乘以输出长度估计在线单条时延。

后续两项对照各自直接从同一父版本派生：先复用每次前向的 KV 页地址计划，再独立将每步 *调度* token 上限设为 1024（当前日志观测到每步总数 2048），保留底层 batched-token 配置及音频预算。关注两种实验各自的单条 decode、首 token、HTTP、吞吐及同动作概率，避免把 decode 的等待转移到 prefill。逐迭代日志只属于隔离诊断。

### RL 与评测按整批输入计时

上游已知道本批所有请求。以批交付到最后一条 HTTP 回执的墙钟为主指标，同时报告总样本、有效结果、有效条/秒、每条 decode 及批尾。只有整批通过业务解析才计为全有效批，失败或不合法输出不从分母扣除。旧连续补位窗口仍用于解释引擎行为，其混合步比例不应套用到整批输入。

当前对照是同一份 BF16 adapter 的 tile512 定制父版本与原生分段图；两侧各 2 批预热、4 批计时，每批 8 段不同真实录音，两侧共用相同批成员、顺序及逐条 seed。组开始时把本组全部请求交给发送池，等最后一个回执后才交下一组；引擎内部仍可动态分块，不等同于 8 条必然落入同一个设备 forward。测量器使用同一个单调时钟记录批释放、每条开始和结束，结果脚本验证没有跨批重叠。传输仍是每条一次 HTTP 调用；本镜像的原生 batch 接口为 8 个会话只提供一个共享 seed，而当前 RL 批中是 8 个不同 seed，不能无声改变采样。知识与指令仍来自各条录音自己的召回。

先前“混合步注意力后捕图”在预热失败，定制 16/16 HTTP 500，配对原生 16/16 HTTP 200。堆栈在图捕获的预热回调中执行 grouped matmul 时，NPU 可扩展内存段预留地址失败；没有得到计时样本。按封闭面板逐条核对意图、响应摘要、容器退出与对照端空闲后释放原 guard，不重发。独立 mixed-decode 算子候选只完成 CPU 路由验证，未在此批量对照中启用。

### 稠密取页基线：四卡等待与 prefill 后半层捕图

从锁定的稠密取页基线另起诊断副本，4×8 新录音、46 个含 prefill 步（9 纯、37 混合），7 层 12 区间，四个 worker 的事件按计时请求、调度步与真实 rank 对账。[逐层区间](engine-profile-bf16/dense-layer-device-intervals.csv)，[分 rank 设备与宿主耗时](engine-profile-bf16/dense-layer-ranks.csv)。七个抽样层每步设备流区间：专家拼接+归并 48.6 ms，attention 输出汇集 44.1 ms，QKV 投影 17.5 ms，attention/KV 11.3 ms。前两项占已测区间约 52%，区间含等待。rank 1 的 QKV/RoPE 为 31.04/24.15 ms，attention 汇集/专家归并为 2.19/14.84 ms；rank 2 对应 16.42/9.36、48.13/51.49 ms。支持跨卡到达时间不齐，但不能把整个区间算作网络耗时，跨 rank 也不能相加。

旧版捕图实际报 rtReserveMemAddress 失败。这次在固定 512 行的完整 tile 上复用每卡一个 prefill 图池，保留输出副本跨回放，卡上保留量不变；同时显式关闭 allocator 的 expandable_segments。两项联合变更不作单项因果归因。新的 A 实例完成 16 条预热、32 条新录音和 5 个 HF 诊断。定制 / 同组原生：单条首 token 4.713 / 2.783 s，prefill 1.589 / 0.954 s，decode 3.714 / 2.339 s，每批首条完整 7.938 / 4.901 s，整批 9.032 / 5.409 s。两侧均 32/32 stop，输出 364 / 398 token，有效 27 / 21 条，prefix 67,456/156,293，音频缓存 0/32。50 个共同动作、4 条完整可比序列概率差零，无独立 top-1。此处原生对照和此前录音不同，只能用后续同输入的独立父实例来判定相对锁定版本的净提升。


相同输入的父实例复验已封闭。两次独立服务先完成相同 16 条预热，再按原顺序计时相同 32 条；两端音频缓存均为零，prefix 相同。四批父版→后半层捕图分别是 11.980→9.199、11.832→9.136、11.188→9.015、11.500→8.779 秒；均值 11.625→9.032 秒，下降 **22.3%**。单条 prefill 2.132→1.589 秒，首 token 6.301→4.713 秒，decode 4.720→3.714 秒。父/新输出 353/364 个 token，302 个共同动作差零，25/32 条完整序列相同；有效分别为 30/32 和 27/32。自然采样仍有分叉，不能视为质量等价证明。锁定后继研究基线 p-dense-tile-graph-c8-v1，正式 rollout 未切换。后续已在同一基线上派发前半层也捕图的单因素试验，单独测量 QKV/RoPE 的前驱影响；输出投影拆分会改变归约次序，未作为本轮改动。

### 第 3 步 checkpoint：32 条自然录音的训练前向精度验收

1,024 行无桩定制引擎以 8 并发自然采样，独立 TP4 完整回放四批；32/32 条录音的全部 371 个动作和原始 logprob 逐值相同。FSDP8 从同一第 3 步 checkpoint 恢复，每卡四条、一次装载，在实际 actor 的 train 和 eval 模式分别评分。两种模式的最大逐动作绝对差和最大整段累积绝对差都是 **0**（上限各 0.01）；top‑1 各 **0/371** 翻转。

370 个位置由独立回放的 raw top 候选直接判定，另一个位置有两个最高分相同。独立诊断只重放其所在的完整一批，不计作性能数据。第一次诊断四个 TP rank 竞争发布同一路径，8 条均返回 500，未知请求为零，未计入验收。修复为每个 rank、每次调用分别落盘；原批 8/8 成功，动作与概率全部复现。分块 prefill 期间同一动作位置每卡有三次回调；四卡观测序列相同，采用历史前进前最后一次，并与实际成功响应对账。在 152,064 项中有两个并列最大值，全词表 argmax 与两种训练模式一致。HTTP 返回候选顺序不用于打破并列。

本次 optimizer 更新次数为零。结论限于该 checkpoint、上述真实录音与批形下的训练前向；性能基线仍为 7.641 秒/批，正式 RL 未切换。下一次实际策略更新需核对梯度、参数变化及导出热载后的 rollout，不能从本次静态评分推断。
