# P 训练提交到启动：前置审查耗时

范围：从封闭轨迹和续训配置已经就绪、调用原训练提交入口开始；分别以训练容器启动和实际更新入口为终点。Rollout、轨迹关闭和提交前证据搬运不计入。历史记录没有控制端提交瞬间的结构化回执，因此历史表从训练主机的配置落盘起算。控制端与训练主机 当前相差约 69 秒，不用两台机器的时间戳直接相减。

| 训练主机上的连续阶段 | 第 2 步成功批次（秒） | 第 3 步（秒） |
|---|---:|---:|
| 训练配置落盘 → 无卡预检通过 | 7.93 | 7.82 |
| 无卡预检通过 → 训练容器启动 | 2.27 | 2.29 |
| 容器启动 → rank 0 发起模型加载 | 19.19 | 19.10 |
| 模型加载开始 → worker 就绪（含 FSDP 构建） | 118.73 | 125.82 |
| worker 就绪 → checkpoint 恢复/优化器核对后进入 cohort 处理 | 25.08 | 24.77 |
| cohort 处理：current/reference 实际评分、数据封闭和消费 | 181.72 | 166.28 |
| rank 0 收下训练输入 → 写出更新意图 | 0.23 | 0.23 |
| **配置落盘 → 更新意图** | **355.15** | **346.30** |

前两行合计是配置落盘后的启动审查与交接，约 10 秒。启动器以原 guard 非阻塞检查占用；两次成功批次没有已记录的排队时长。后五行已经占用训练容器，其中模型与 checkpoint 就绪和同动作评分是实际训练准备。两个阶段分别报告，避免把约五分半钟都归给门禁。两次历史失败的返工另记，不计入成功尝试的正常启动耗时。

已优化原 `stage_bounded_actor_step.py`：原先逐条远读训练配置、退出回执、checkpoint 清单和 8 份 rank 回执，再逐文件 SCP 发送暂存输入。现在一次拉取同样的回执、一次投递同样的源码和配置快照。继续核对原 checkpoint 摘要、步号、8 个 rank、发布权重身份、模型源码和实际 cohort；预检与启动的 guard、设备占用、容量和 boot 校验保留。训练逻辑和 rollout 无变化。

在训练主机用固定镜像对第 3 步的真实封闭输入做无卡交替 A/B。用 `STAGE_ONLY=true`，每次设置独立的 `RUN_NAME`，其余配置相同；检查 2 组、103 个文件。端到端命令耗时为旧版 6.96–7.06 秒（3 次，中位数 7.02），合批版 6.54–6.80 秒（3 次，中位数 6.68），约省 0.34 秒。本对照不启动训练。最终版本追加计时后仍正常通过；错误 checkpoint 摘要在创建训练目录前被拒绝。

最终版本的单次计时：取前驱回执 0.05 秒，配置与成对源码核对 0.11 秒，投递 0.17 秒，无卡预检 6.21 秒；入口合计 6.54 秒。后者内含约 1.07 秒的宿主检查及准备、5.07 秒的容器阶段，其中约 4.24 秒执行实际检查流程。容器阶段与其子项不可重复相加。新提交日志在 stderr 输出结构化阶段耗时，`CAPTURE-PREFLIGHT.json` 保留宿主和容器时间分项。

后续优先级：

1. **前置审查**：在封闭产物生成后立即启动无卡审查，使其尽量早于最终训练派发。对镜像、成对算术源码、固定数据索引等稳定依赖复用已封闭的带版本回执。每个新窗口仍核对轨迹清单、实际策略与 checkpoint；占卡时实时核对 boot、guard、设备和容量。现有测量表明，即使覆盖整个无卡预检，可移出最后一次派发的时间也约为每窗口 6 秒；尚未实测重叠比例。先细分这 4.24 秒的实际检查，再决定是否值得拆成独立可复用凭证。
2. **若目标是更早开始参数更新**：优先评估原控制器下的常驻 FSDP8 actor，量化重复进程、模型加载和 checkpoint 恢复的节省。实际更新前仍要独立核对本轮新动作的行为分数、参考分数和消费分母。先统计 166–182 秒 cohort 处理里的 current/reference forward、数据封闭和加载各占多少；只对冻结 reference 的完全相同条件及动作复用分数。新的采样结果和精度门槛照常验证。

历史分段使用训练配置、预检、容器接管和 rank 0 的加载、worker 就绪、cohort 接收及更新意图回执。复现实验沿用[续训模板](../../tools/system_rl/runtime_repairs/BOUNDED-CONTINUATION.template.json)和本地部署 profile，使用同一批封闭输入与独立尝试名。
