# 运行基座稳定性审查与修复方向

反复失败的主要原因是局部修复没有形成统一的部署契约：输入准备、实际服务能力、任务协议和恢复流程分别验证，下一轮换任务或目录后又出现接缝错误。修复应复用现有请求日志、资源租约和持久队列，收敛适配入口。

本次逐条核验30次真实请求，均因结构化输出后端不支持 `uniqueItems` 被确定拒绝，没有未知请求。原终态记录的分配成本合计约0.10585卡时；响应未提供usage，token与金额成本未知。本地模拟测试覆盖了框架调用和日志回放，但没有验证实际服务的grammar compiler。删除不支持的schema字段并保留输出去重后，后继已有真实成功响应；这只能证明执行链恢复，不能代替完整基线结果。

历史证据还确认了输入准备与恢复使用不同依赖基座、容器路径假设、断链后终态等待未重挂、本地存储容量耗尽、服务上下文预算不一致和设备编号映射等问题。两次文件系统内核异常属于独立故障域。不能把所有事故归因于存储，也不能把模型预测错误或同输入输出波动直接认定为工程故障。

有两项缺陷在执行前被审查发现：相同请求内容的不同样本可能错误共用日志寻址，以及传输指标覆盖阶段指标。没有证据表明它们已经污染实验。现有安全机制也有实证：断开本地观察连接后，同一远端任务可以继续并完成1635条有效结果，未知请求为零；该演练不覆盖服务器重启或长期网络分区。

修复优先级：

1. P0仅两项：真实服务能力契约；输入与部署就绪闭环。前者绑定实际服务端构建、补丁、grammar编译器、分词模板与生效预算；后者交付包含运行入口与依赖的可运行包，启动须核对输入、版本、部署及FIT一致。准备正确且无需刷新时显式返回成功的无操作结果；刷新失败或绑定不一致不得启动。
2. P1扩展共享入口，固化已修的请求身份与计数语义、安全恢复共用化，去掉其他历史实验路径与固定分母；归档终态事件只消费一次，按实际存储分区管理临时副本。
3. P2在有意义的基线通过后优化增量归档和CPU开销，依据真实数据优化吞吐；底层内核修复安排独立维护窗口。

客户端固定镜像与服务端推理镜像分别取证，客户端测试通过不能证明服务兼容。离线检查复用实际服务同一编译入口、后端及补丁和分词资源，保存逐schema编译回执；无法CPU加载时明确标未验证，不以模拟结果代替。再用首个正式请求进行在线契约检查。首个结果直接计入正式分母，无需反复smoke。后端grammar、实际音频接入和设备布局需要真实环境验证；本地解析、拒绝回放、日志身份、断链控制流可做CPU故障注入。

已知响应从原日志恢复，不重发；已知拒绝在修正请求后使用独立后继；发送后响应未知时只追踪和核验，不能盲重试或删除全部锁。CPU输入准备在推理租约前完成，任务脱离连接运行，正常观察每600秒或由明确终态事件触发。

本次只交付审查及实施方案，没有修改运行中的实验，没有新增模型调用。完整运行成本、停机损失和人工沟通成本在证据不足时保留未知，未编造总tokens或利用率收益。

修复只面向下一发布版本，不暂停当前已运行实验。业务候选过量不归工程事故，单次设备利用率快照不能代表长期利用率。上述修复与真实后端验收尚未执行。
