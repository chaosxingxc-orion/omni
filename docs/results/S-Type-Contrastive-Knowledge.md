# 意图内槽位区分：从单卡定义到对照知识

## 用户纠偏与评价口径

将意图内错误的业务总称调整为“混淆提取”，保留FP/FN作为可对比的统计量。相邻类型替换、无表达却确认、应有类型漏掉是不同机制，不能仅凭FP与FN同时出现就断言二者发生替换。当前任务只识别类型，不要求输出槽值或转写。

## 缺失的表达层

已有单卡说明每个类型是什么，但同意图内的相邻类型应有一份共同审阅的边界定义：意图条件→表达的语义角色→与相邻角色的区别→实际存在性→类型集合。不能把独立卡片分别写得更强硬，造成彼此矛盾。

新增的对照知识与单卡共用一套来源：intent_id、type_a/type_b、共同易混语义、区别所依赖的关系/角色、正反TRAIN证据、何时可共存、不能据什么判断、来源冲突/未覆盖状态。只覆盖实际易混关系，不构造所有类型的笛卡尔积。知识供给按意图直接组装，不要求先运行模型知道真实槽位类型。

## 三个值得优先核证的区分维度

|当前意图|易混类型|应表达的区分轴|需要反例保护|
|cooking_recipe|food_type / ingredient|请求中的制作对象与配料/替换材料角色|同一个食物词随语义角色变化；现TRAIN边界不一致，不能写绝对规则|
|calendar_set|person / relation|人员姓名/称呼与关系/职务描述|一句话可以同时给出姓名和关系，不能强制二选一；开放人名不靠大小写|
|play_music|artist_name / song_name / music_genre|表演者、作品和风格在播放请求中的角色|同一词可以作不同实体名，仅凭关键词不能唯一映射|

以上是角色区分假设，具体可执行规则必须核对合法TRAIN标注。已读现卡：ingredient正文明确写not consistently；artist_name正文提到person；person卡允许姓名与角色分别提取。它们说明需要关系型对照而非互斥词典，不能自动把业务直觉改成数据金标。

## 边界知识至少回答五件事

1. 在当前意图里，这个类型承担什么角色，而非它一般指什么。
2. 与哪个相邻类型容易混淆，区分依据是什么关系，而非只列词表。
3. 同一个表达在什么条件下归A或归B，合法TRAIN有没有对应的近邻反例。
4. A与B能否同时出现：同类名词不等于互斥，多个不同表达可分别承载不同角色。
5. 本句没有表达该角色、角色存在但值不具体、声学/语义未确定如何区分。不能由意图或示例补齐。

## 示例消费与评测

相似问应提供角色对照：保留相关锚点，补充能展示相邻角色差异的真实来源例。不同场景拼出的对照不一定有效；不能把未标注当可靠负例，更不能用开发query答案生成配套例。无合法可辨对照时显式记录缺证据，不虚构。

模型输出仍是类型集合，不要求隐藏思考、槽值或长解释。before_model_call注入意图内类型索引、单卡及少量边界对照；after_model_call只做合法性和结构检查，不根据关键词硬替模型改类型。

评价分层：类型集合exact；存在性混淆（多提/漏提）；相邻类型替换候选；共存关系处理；争议标注/信息不足；协议错误另列。相邻替换只有轨迹和语义证据支持才归因，类型集合层的FP/FN交叉只是线索。未改动输入的输出波动作为归因限制。按整类修复/回退验证，不依据query gold路由。

## 实施边界

先由知识CPU子进程对合法TRAIN构建一类小规模对照知识及相反证据，给主线程审查；不覆盖原知识快照。独立实验不同时改顺序或示例选择。当前A纯顺序、B+C组合仍按各自固定变量推进。对照知识是下一轮候选，未部署、未宣称收益。
