## System objective and comparison

The unit of intervention is a complete continuation: original Perception,
a source-bound interpretation of its candidates and actual TRAIN examples,
matching intent distinctions and slot explanations, Solver, independent
Reviewer, Planner, bounded revision, and final delivery. Complete terminal
quality decides whether this action is useful. Coverage and intermediate
repair are diagnostic; neither is a system return.

The next matched policies use common rendering and role instructions. The
control renders the original candidates; the recovery policy preserves them
and appends selected-exemplar-supported candidates up to eight. Both use the
same actual exemplar selection, release versions, task inventory, serving
geometry and complete graph. Both explicitly expose corresponding released
intent distinctions. The treatment alone gains added-candidate explanations
under a declared extra slot-card budget. This is a coordinated policy
comparison, not a pure causal estimate of candidate count or one component.

Do not reuse the old candidate-only Solver wording. Its future common
replacement must allow joint intent/entity judgment from original and derived
cues, keep the full legal inventory, deny exemplar frequency any confidence
interpretation, and preserve Solver answer authority. Reviewer evaluates speech
support and alternatives; Planner decides continuation. No forced lookup or
closed Reviewer-availability recovery is part of this action.

The historical 93.12-percent cap-eight projection is motivation on two sealed
source runs, not promised coverage or achievable accuracy of the new policy.
The 95-percent coverage goal remains open. No unseen DEV/test data is admitted.

## Configuration surface and execution

The existing registered slurp-candidate-semantic-v1 provider accepts the optional
candidate_supply.solver.exemplar_candidate_proposal object:

- mode: original-only or append-selected-exemplars.
- exemplar_store_id: an existing TRAIN train-exemplars store with a same-phase
  ordinary Solver selection.
- intent_store_id: an existing released authored intent-boundaries store.
- max_candidates: total proposal cap, 3 through 32 and within the legal inventory.
- max_added_slot_values: separate positive budget for added candidates' unique
  slot explanations; it never replaces the baseline max_total_values.

The first integration accepts the original single bounded max-three Perception
route, with no standing fallback or candidate refresh. It requires the native
complete graph. Role/node context transforms, context compaction, acquisition,
Solver groups/variants and whole-policy selectors are refused in combination
until explicitly integrated. The candidate provider is still the registered
shared provider; no controller, executor, model service or private retriever is
added. Historical omitted configuration remains unchanged.

The named-store router consumes the actual same-visit local rank/fusion result
before qualifying exemplar IDs. It validates query, snapshot, selected values
and released-store bindings, creates one proposal, and records source custody.
Revisions may rebind their retrieval receipt to a new QueryState but must retain
the same selected values, proposal interpretation and first source selection.
The separate proposal never replaces or edits Perception.

Slot selection first runs the existing baseline round-robin. Its exact result
is retained as a prefix. A second use of that same selector appends only new
cards for added candidates; shared cards consume no new quota, unused budget
does not refill original candidates, and omitted mappings are retained.
Intent relationships are rebuilt from their released authored source through
the existing released-target index. All proposed intents require a released
distinction. The acquired IDs enter ordinary PhaseSupply, rank/fusion and
QueryState custody.

The flight-owned proposal callback checks that original Perception and the
required examples/cards are visible. The same derived text reaches every
downstream actual native request, including revision. Its block has a stable
proposal hash and source URI, without private source IDs in the text. Actual
request, response, query and per-role bindings are recorded separately under
ORG and in the complete episode receipt.

Sealing requires the declared proposal receipt. Bundle validation joins the
proposal to the raw Perception state, deterministic exemplar interpretation,
every completed or interrupted downstream contact, the actual supplied text
and its ORG record. Raw states, requests and outputs remain unchanged.
Finite completion at each of the four roles retains the whole row and the
shared delivery/abstention behavior; interrupted contacts are not dropped.

The preparation volume estimate includes extra slot cards, intent distinctions
and proposal text using the common text formatter. This is a coarse UTF-8
envelope, not a capacity receipt. All real requests must still pass the shared
native fit gate before dispatch; no output-cap reduction is authorized.
