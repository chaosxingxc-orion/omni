# Compact, source-addressed proposer feedback

Recorded by ChatGPT root under owner decisions 214, 215 and 217. This is prospective offline engineering evidence. It does not authorize a proposal, replace a spent slot, or modify the active GPU worker.

## Change and scope

The preserved L-1-2 failure showed that repeating a large artifact page could prevent the next proposer contact from fitting its cumulative input allocation. The new opt-in `compact-feedback-v1` capsule profile places the complete family summary and an outcome overview in the initial context, with an index covering every sample. It retains immutable full feedback, policy history, construction sources, terminal records and traces behind the same hash-bound artifact reader. This is a presentation change, not a new reward, a new runtime knowledge store or a relaxation of the complete-family READ gate.

Each sample has a full case view containing every own-branch member. Separate paired briefs compare the parent with each other member. Briefs include official native counts, utility, reliability, model/tool contact counts and explicitly truncated terminal and role-response prefixes. Full case views retain complete-source character addresses, including original JSONL delimiters. Missing responses are marked. Source tails, request bodies, tool payloads and omitted members remain addressable; prefixes are never described as complete trajectories.

The overview separately counts repaired correct answers, damaged correct answers, unchanged native counts, unresolved changes and unreliable execution. Correctness here means correct intent and zero exact-slot FP/FN; these descriptive categories do not replace official SLU-F1 or determine adoption. One representative per nonempty comparison/category is chosen by the smallest fixed-seed sample hash, not by its gain. A/A comparisons are explicitly labeled as variation. Every case remains in the index, including cases not selected as representatives.

Blind capsules contain no feedback or derived learning views. Both branches must use the same explicitly admitted profile. The launcher rejects a profile mismatch against the provider admission, registration or either branch's capsule. Existing registrations continue to use `full-index-v1`; reconstruction of both original L-1-2 and B-1-2 initial requests is canonically identical to their preserved dispatch requests.

## Budget behavior

Compact reads are limited to 2,048 characters per contact. The initial request states the indexed omissions and reading cost. Each continuation states its remaining cumulative input allowance, remaining contacts, previous reported input usage and the conservative bound of its complete serialized request, including the notice itself. It warns that another tool read needs another repeated-context call. The proposer may submit no change when evidence is insufficient; it must not invent unread evidence.

The existing owner217 bounds remain unchanged: 32,768 cumulative input tokens, 4,096 metered output acceptance and at most four contacts. The full UTF-8-request-bytes-plus-4,096 bound remains authoritative before contact. Provider usage remains authoritative after contact. There is no tokenizer discount, invented probability, history deletion, automatic retry, replacement allocation or claim of equal realized compute. A presentation profile is not a promise that any arbitrary sequence of reads will fit.
