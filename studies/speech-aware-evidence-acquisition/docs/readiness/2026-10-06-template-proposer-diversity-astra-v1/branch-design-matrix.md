# Prospective branch design matrix

This matrix is a menu of policy mechanisms, not a generated experiment population. Allocate only the candidate positions in the next admitted config. Do not allocate these rows to current Update5 identities, replace its spent slots, add runtime calls or treat matrix coverage as evidence of quality. All procedures below run internally inside existing node visits and use existing output fields only.

## Mechanism families

| Family | Decision procedure and node responsibilities | Preferred edit scope and legal assembly | Predicted signature; principal counter-signature |
| --- | --- | --- | --- |
| A. Applicability before assignment | Solver identifies expressed arguments, matches their relational role to the operative supplied definition, then chooses type and extent. Reviewer independently asks whether that definition applies before claiming omission or incorrect assignment. Planner routes an established discrepancy. The distinguishing condition is audible content that does not fulfill a legal role; mere presence is insufficient. | Solver/Reviewer; preserve Perception/Planner unless the handoff requires a change. Either history mode. | Higher initial/final entity quality, fewer false fills. Risk: conservative applicability drops genuine arguments or lowers recall. |
| B. Challenge with a burden of evidence | Reviewer begins by identifying what supports the current decision, then tests the strongest concrete contradiction. An unresolved question is distinguished from an established error inside reason. Planner verifies the contradiction or uses the existing permitted lookup for a material legal distinction. Solver can return the same supported complete answer after REVISE. | Reviewer/Planner, optionally Solver. Local history favors independent current-state judgment; full history remains legal if reanchored. | Lower false alarms and harm to correct drafts while retaining detection and repair. Risk: agreeable review hides omissions or treats unsupported drafts as presumptively correct. |
| C. Coverage and support as separate directions | Solver constructs an internal speech-to-argument inventory before serialization. Reviewer first searches for a concretely expressed applicable argument omitted from the draft, then checks emitted fillers against speech. It never fills a conventional slot roster. Planner distinguishes actual omission from label uncertainty. | Solver/Reviewer; add Planner only to repair this distinction. Either history mode. | Fewer false negatives or empty-output omissions, improved raw repair. Risk: audible but inapplicable words become false fills; alarm volume rises without repair. |
| D. Criterion-based counterfactual | For a genuinely ambiguous current assignment, Solver or Reviewer identifies the single supplied criterion under which the competing interpretation would be right, then checks whether available speech satisfies it. No exhaustive alternate answers or extra calls. Planner looks up only an unresolved meaning/scope criterion within its existing allowance. | Solver/Reviewer, optional Planner. Either history mode; examples remain non-exhaustive. | Better disambiguation and alarm precision without more label hedges. Risk: imagined counterfactuals manufacture uncertainty; higher latency and unchanged repair. |
| E. Relation before inventory | Perception distinguishes requested operations using action, object and modifier attachment. Solver chooses among those original candidates from the whole relation before extracting values, but still checks all legal entity types. Reviewer checks relational attachment separately from lexical familiarity. | Perception/Solver with optional Reviewer. Query placement is a testable assembly axis. | Better intent/candidate coverage with preserved entity F1. Risk: a plausible frame erases atypical supported arguments; a better candidate list does not ensure Solver selects correctly. |
| F. Repair with explicit dependencies | Solver decomposes a grounded repair into presence, legal type, extent and original-candidate intent. It updates only the decision and dependencies actually implicated by evidence, then returns the complete object. Reviewer states which criterion is disputed in existing fields. Planner refuses broad re-extraction for a narrow finding. Invalid JSON still requires full representation reconstruction. | Solver/Reviewer/Planner or a focused subset if parent handoffs already suffice. Either history mode; no patch output or new memory. | Fewer correct-to-wrong transitions while retaining wrong-to-correct yield. Risk: overly local repair preserves a globally wrong interpretation or makes a needed coupled repair impossible. |
| G. Reconcile current state against available history | With full history, Reviewer checks whether an earlier criticism still applies to the latest draft and whether actual returned guidance resolved it. Contrast with independent latest-state review using latest-solver-and-local-tools. Planner never equates repeated criticism with corroboration. | Reviewer/Planner plus history setting; preserve Solver when compatible. Full-history variant may reason about prior turns; latest-only variant must not require them. | Less stale criticism and harmful reopening, or improved use of genuine returned guidance. Risk: full history anchors on prior mistakes; latest-only mode loses useful context. History differences are an assembly hypothesis, not new memory. |
| H. Separate operation and entity objections | Reviewer communicates an operation-only limitation in checked and never fabricates a slot finding for it. Planner distinguishes a concrete operation mismatch from a completed check. Solver changes intent only to another original candidate with speech support, and reevaluates only necessary entity dependencies. | Reviewer/Planner/Solver, optionally a focused Planner-only change. Either history mode. | Better intent/full correctness with preserved entity decisions. Risk: free-text checked is not a typed error channel; ambiguity causes spurious routing or missed intent repairs. |
| I. Complete construction before serialization | Solver settles the requested operation and full applicable extraction before emitting the required object. Reviewer recognizes unusable representation without inventing its contents; Planner routes the available representation repair directly. Reconstruction cannot use empty entities as a parser fallback. | Solver with optional Reviewer/Planner. Query placement can be held fixed or tested separately. | Higher raw parsing availability and reliable completion with unchanged or higher entity coverage. Risk: cleaner syntax masks lost content; more internal construction increases cost without business gain. |

Families may share safety invariants. They are counted as distinct only if the actual emitted role text contains different operational decision rules. For example, B versus C differs when evidence supports the current emitted entities but an unrepresented applicable argument remains: B's support test alone can accept, while C's mandatory coverage direction searches for that omission. A complete B policy must still respect baseline coverage requirements; emphasize its distinctive burden for proposed edits rather than disabling essential checks. D differs from B by testing a discriminating criterion for a genuine competing interpretation, not by replacing "contradiction" with "contrast".

## Allowed combinations

Combine A+C for complete applicability and coverage, B+F for criticism precision and bounded repair, D+F for disambiguation with dependent edits, E+H for operation handoff, or G+B for history-aware evidence checking. Other combinations are legal if their preconditions and responsibilities are coherent. Assign one primary family and at most one secondary family for the diversity audit; incidental invariant checks do not count as extra mechanisms. Avoid a universal omnibus policy containing every family: it erases contrasts, consumes capacity and makes failures harder to interpret.

Do not combine a strict "only proven defects may be mentioned" Reviewer with a Planner whose lookup depends on seeing unresolved legal questions. Use the existing reason field to distinguish the material unresolved question from established error, without new schema keys or pretending certainty. Do not require revision deltas in latest-only review. Do not impose an intent-specific entity roster under any family. Do not replace the native action limit with a custom confidence threshold or a second revision.

## Assembly axes

The compiler supports exactly these three binary choices:

| Field | Legal values | Business hypothesis and tradeoff |
| --- | --- | --- |
| context_layout.native_role_query_placement | null; before-speech-v1 | Placement may clarify the current task instruction or change salience. It supplies no new evidence; effects need measurement. |
| node_context.tool_schema_rendering | constant; per-role | Role-specific presentation may reduce irrelevant tool salience. Constant presentation may preserve useful context but never grants authority. Token savings are secondary. |
| node_context.reviewer_history_scope | full; latest-solver-and-local-tools | Full history permits rechecking actual prior questions/results; local state may reduce stale-draft anchoring. Verify visibility compatibility. |

These define eight legal assembly combinations, not a requirement to fill an eight-cell factorial. Do not add new placement values, reorder knowledge packets, mask evidence, summarize history, or invent memory fields. An assembly contrast counts separately from semantic mechanism diversity. If two slots are intended as an assembly-only contrast, their complete non-assembly role behavior must be aligned within their legal parent bindings and this must be recorded; differing parents otherwise confound that contrast. Prospective contrasts are diagnostic designs and do not establish causal node effects.

## Configured allocation and anti-collapse

Let K be configured proposal positions; let C be positions with a genuine edit after any prospectively reserved no-change positions. Keep K fixed. The proposed rubric targets at least min(C, 6) independently justified primary mechanism families and no family occupying more than max(1, ceil(C/3)) changed positions. Six is a versioned coverage target, not a hardcoded experiment population size. At least min(C, 2) edits should be focused on one role or one supported assembly axis when feasible without breaking handoffs. Include a coherent multi-node mechanism when C allows and its targeting rationale justifies one. These are pre-emission design targets and post-emission diagnostics, not grounds for replacing spent proposals.

Prefer at least min(C, 3) supported assembly combinations among changed complete systems when the mechanisms allow it; record a reason if visibility compatibility prevents this. Do not add meaningless assembly flips to satisfy a count. A no-change record contributes to total position accounting and inherited population diversity, but never to achieved edit-family coverage. Invalid proposals count in K and attrition, not in validated mechanism coverage. Report the realized denominator and every shortfall. The root may bind different numeric targets prospectively; never adjust them after seeing results.
