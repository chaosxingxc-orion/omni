### 1.1 Three corrections to the plan, each forced by measurement

1. **The label space is 151, not 152.** The registry declares 152 tools; gold uses 151 of them
   as a primary tool. `getLockStatus` never appears as a gold tool anywhere in the 30,733-item
   pool, so it cannot receive a sample-bound facet (`KeyFacet` requires non-empty
   `source_sample_ids`). The plan's "≥1 exemplar per tool (all 152)" floor is therefore met at
   151/151 of the reachable label space, and the 152nd tool is named rather than silently lost.
2. **`tool_id` is not a join key.** Ten `tool_id` values carry a different `tool_name` in the
   manifests than in `tools_registry.csv` — `70` is `setLighting` in gold and `setLightState`
   in the registry, `82` is `setSecurityMode` versus `armSecuritySystem`, and so on. The build
   joins by NAME, which is also what `reproduction.toolcall_scoring` compares. Any downstream
   code that joins on `tool_id` will silently mislabel ~10 tools.
3. **`query_idx` is shared ACROSS tiers.** 4,646 distinct values over 8 tiers; 2,495 of them
   appear in more than one tier. tier1 `query_idx=2100` and tier5 `query_idx=2100` are two
   different phrasings of the same base scenario against the same tool. That makes the
   `query_idx` BLOCK, not the item, the unit that carries leakage between a construction pool
   and an evaluation tier — the single most consequential fact in this report for split
   governance.

## 2. Split governance — the partition proposal

**Audio2Tool ships no formal train/dev/test split.** It ships 8 tier manifests and nothing
else; there is no `train.jsonl` analogue, no split column, no upstream partition file. Stated
plainly: **a construction-versus-evaluation partition has to be constructed, and the
construction is a design decision that must be defended, not an assumption that can be
inherited.**

This section is a **PROPOSAL**. It is landed as
`docs/receipts/knowledge/a2t-partition-proposal.json` (sha256 `3bbf77a3…8678a1`), deliberately
**not** under `docs/receipts/probe-samples/`, because `data.audio2tool.audio2tool_receipts`
globs that directory and any file placed there would silently EXPAND the carrier's frozen
loadable universe. Registering the evaluation tier as flyable is later campaign work with its
own preregistration.

### 2.1 The rule

Partition the **4,645 usable `query_idx` blocks** three ways (policy
`saea-a2t-block-partition-v1`, seed **20260807** — the carrier's own frozen seed):

1. **RESERVED-EXPOSED — 374 blocks, 2,061 units.** Every block touched by the frozen exposed
   400. Held out of BOTH sides. The exposed 400 may still fly as the plan's §3.3 SECONDARY
   comparator; holding its cross-tier siblings out of the KB too is what makes that secondary
   reading safe against the same knowledge base.
2. **EVAL (proposed A2T-DEV-400) — 400 blocks, 400 items.** A seeded tier-stratified draw,
   50 per tier, each item from a DISTINCT block, whose whole block is then reserved. Tiers are
   processed in ascending order of candidate count (`tier8_intent_blending` first, with only
   821 items; `tier2_parametric` last) so no tier can be starved by an earlier one. One wav per
   drawn unit — the lowest item id — so the roster never contains two near-identical renderings
   of the same text. Proposed split identity hash `4d0196ec…df2f90`.
3. **CONSTRUCTION — 3,871 blocks, 12,601 units, 22,951 items.** Everything else. This is the KB
   pool.

An extra candidacy rule: an item may enter the evaluation tier only if its gold primary tool has
**≥8** units in the exposure-free pool, so the build's per-tool floor can never be starved by
the draw. Five tools are construction-only under this rule and are named rather than dropped
silently: `adjustVolume` (2 units), `controlLocks` (2), `getClimateState` (7),
`setAudioVolume` (2), `setChargingLimit` (2) — 15 units, 0.09% of the pool. Four of the five are
rare aliases of the ten `tool_id`/registry-name disagreements in §1.1.

### 2.2 What it costs and what it buys

Block-level rather than item-level disjointness costs real data: 2,061 units go to the exposed
reserve and the 400 eval blocks pull ~2,176 further units out, so the construction pool is
12,601 of 16,838 usable units (74.8%) rather than ~16,400. That is the price of being able to
say, without qualification, that no construction exemplar is a different-tier rendering of an
evaluation item's own base scenario. On a synthetic corpus that re-renders the same scenario at
eight difficulty tiers, the weaker item-level rule would not survive a reviewer.

Machine-checked properties, all fail-closed inside `propose_partition`:

- eval ∩ construction sample ids = ∅
- eval ∩ exposed-400 = ∅
- construction ∩ exposed-400 = ∅
- eval blocks ∩ construction blocks = ∅
- every gold tool retains ≥1 construction unit (151/151)
- the draw is deterministic and pool-order independent (unit-tested against a shuffled pool)

### 2.3 The limitation this proposal must carry

**400 evaluation items cannot cover 151 tools.** The proposed tier touches **96** distinct gold
tools. A per-tool breakdown of a G2 confirmatory result will therefore be sparse, and any claim
about "the tool label space" from n=400 is a claim about the 96 tools that were drawn. The plan's
§3.5 power argument (n ≥ 400 unexposed) is about the pooled tool-accuracy interval and is
unaffected; the label-space coverage limitation is separate and must be stated wherever a
per-tool table appears. If G2 registration wants broader tool coverage it must either grow n or
stratify the draw by tool as well as by tier — a decision for that preregistration, not this
report.

### 3.1 The shape, and the one bet it makes

Generalizing the SLURP builder rather than editing it (`rails/knowledge.py` and
`rails/knowledge_build.py` are untouched and still byte-frozen, because the locked baseline
cites their hashes):

- **Content facets** — the invocation utterance text, one per construction unit. For
  `tier7_multiturn` the facet keys on `user_request` (the final user turn), NOT on `query` (the
  whole conversation transcript), because the runtime protocol sends only the final user turn's
  wav. Keying on `query` would build a KB whose keys the runtime percept can never match.
- **Label facets** — one per gold tool, parented `domain → category → tool`, the exact analogue
  of SLURP's `scenario → action → intent`. Each carries the registry signature, description,
  defaults and constraints.
- **Value bundles — the campaign's A2T-specific bet.** SLURP's values carried a label. Here each
  value carries the tool identity, the registry signature/description/defaults/constraints, the
  exemplar's own argument pattern as `key=value` pairs, the other argument patterns observed for
  that tool, the argument values observed for that tool across the construction pool, and the
  tool's argument-pattern prior. The bet is aimed squarely at the A0 verdict's finding that the
  dominant loss channel is argument construction (+30.0 pp tool-acc→EM gap), not tool selection.
- **Prior facets** — `p(argument-pattern | tool)` and `p(argument-key | tool)` from full
  construction-pool counts, the statistical analogue of SLURP's `p(entity_type | intent)`.
- **`prior_score`** on each value is `p(tool | category)`, the analogue of SLURP's
  `p(intent | scenario)`, so `kb_policy`'s prior-mass recall path works unchanged.

**One deviation from the SLURP dimension set, taken deliberately and reported rather than
hidden: the `speaker` dimension is OFF.** SLURP speakers are real people whose identity carries
acoustic and distributional information. Audio2Tool speakers are synthetic voice assignments
from voice banks, they carry no tool-selection information, and 821 tier8 rows have no speaker
id at all. The dimension stays representable (`dimensions` accepts `"speaker"`) and can be
switched on if G1 wants it. This is a knowledge-construction decision, which the plan §3.2 puts
in scope; it is NOT a change to the locked cell's knobs, which are carried unchanged.

## 4. The G0 gate — lexical reachability ceiling

Policy `saea-a2t-lexical-ceiling-bm25-v1`. Receipt
`docs/receipts/knowledge/a2t-kb-lexical-ceiling.json` (sha256 `624d85f9…3703fc`).

### 4.1 Why lexical, stated before the number

The SLURP ceiling ranks content facets by cosine against a flown query embedding. Producing an
embedding on this carrier requires the pinned `qwen3-emb` sidecar, which is a **tool contact**,
and G0 is registered at zero contacts. **No dense ceiling was computed and none is reported.**
Instead: a locally implemented, deterministic Okapi BM25 (k1=1.5, b=0.75; tokenizer = lowercase
runs of `[a-z0-9]`; ties broken by ascending facet id; zero-score documents appended in facet-id
order, the worst case for the gold facet and therefore the conservative convention), ranking all
12,601 content facets against each evaluation item's own gold-side query text.

**The proxy cuts both ways and both directions are stated at every citation:**

- **Pessimistic in the ranking function.** Token overlap cannot follow a paraphrase the way a
  dense encoder can. A dense ranker over the same facets would place at least some gold-tool
  facets higher.
- **Optimistic in the query representation.** The query text here is the manifest's own
  transcript of the spoken command. At runtime the controller never sees that text; it sees a
  speech-derived percept (in the locked two-contact form, a first-contact knowledge decode).

Neither direction dominates, so the honest description is: **a ceiling on the LEXICAL channel
conditioned on a PERFECT TRANSCRIPT.** The gate treats it as a **necessary** condition, never a
sufficient one — if even this optimistic-transcript, closed-pool ranking could not put a
gold-tool exemplar in the top 5, no downstream fusion policy could.

any k.

### 4.3 The near-duplicate audit — the objection answered before it is raised

The first thing a reviewer says about a high ceiling on a synthetic corpus is *"your knowledge
base contains paraphrases of the evaluation items"*. Measured, per item, as the maximum token
Jaccard against any construction content facet:

| | value |
|---|---|
| Median max-Jaccard | 0.4318 |
| p90 | 0.6250 |
| Max / min | 1.0000 / 0.2000 |
| Share ≥ 0.9 | 2.75% (11/400) |
| Share ≥ 0.8 | 3.75% (15/400) |
| Share ≥ 0.5 | 38.75% |
| **Novel subgroup (max-Jaccard < 0.8)** | **385 items** |

**Novel-subgroup recall@5 = 0.7844** against a pooled 0.7925 — a difference of 0.8 pp. The
ceiling is not near-duplicate memorization. (Recall@1 on the novel subgroup: 0.5455; @16:
0.8935; @128: 0.9844.)

Note that the block partition is what makes this true: the 15 near-duplicates that remain are
same-tier neighbours from different base scenarios, because every cross-tier re-rendering of an
evaluation item's own scenario was already removed by §2.1.

## 5. Limitations — read these with the numbers

- **Lexical proxy, both directions.** §4.1. Cited nowhere without both halves.
- **Perfect-transcript conditioning.** The ceiling uses gold manifest text as the query. The
  runtime query is a speech-derived percept. The gap between them is unmeasured on this carrier
  and cannot be measured without contacts.
- **The partition is a PROPOSAL, not a registered split.** No receipt was written into the
  loader's frozen sample universe. G1/G2 may adopt, resize or re-draw it; if they re-draw it,
  this ceiling does not carry over.
- **96 of 151 tools in the evaluation tier.** §2.3. Per-tool G2 tables will be sparse.
- **Per-tier ceiling versus A0 is unpaired**, on disjoint populations, n=50 per cell. §4.4.
- **The corpus is synthetic.** Invocation texts are generated and the speakers are synthetic
  voice assignments. The near-duplicate audit bounds the memorization concern within this
  corpus; it says nothing about whether the corpus resembles real spoken tool use.
- **5 quarantined units and 1 registry tool with no gold instance** are permanent properties of
  the shipped asset, not of this build. §1.2, §1.1.
- **`a2t-gold-v1` scorer semantics are interpretation, not ground truth** — the A0 verdict's own
  limitation, inherited here in full, because the gold tool names this ceiling scores against
  come from the same parser.
