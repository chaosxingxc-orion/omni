## Knowledge construction and consumption

The shared compiler now has an opt-in tool-activation-scope-v1 value projection.
Every value contains the exact tool name, public domain, public category and full
public operation description. The registry must map exactly to all 152 compiled
cards by name, signature and description. Only underscores in public domain and
category are humanized. Old views and their identities are unchanged.

Root checked every new value against its public source. The 152 values total
35,153 characters, averaging 231.27 characters rather than the older activation
view's 364.47. Shorter content is not the objective or evidence of higher quality:
the discarded material was a generic Avoid list and unrelated lexical neighbors,
while every tool's own complete public description is preserved. The separately
published parameter store retains its richer explanatory content.

The lexical contrast artifact remains held and unpublished. Its irrelevant
neighbors are not silently replaced. The scope successor has its own compilation,
snapshot, release and root-review hashes. All source bytes stay outside Git.

Examples of what the public source actually distinguishes include vehicle lock
status versus smart-lock status, and a cabin-zone temperature operation. Some
pairs, including rebootDevice and restartDevice, still have overlapping public
meanings. Domain/category alone does not establish an activation boundary. The
system may inspect parameter roles for additional evidence, but must not invent a
distinction or derive a runtime rule from evaluation error pairs.

The activation values contain no evaluation labels, reference transcripts,
observed evaluation confusions or generated rules. Positive retrieval keys retain
their previous representations, but this version does not compute or consume
automatic speech-to-key retrieval. The compiled corpus keeps permitted
construction provenance; it is not inserted wholesale into activation values.
Parameter meanings remain an independently bound, previously prepared source.

## Actual role behavior

The shared EvidenceAgentController, FlightRuntime and OpenJiuwen execution path
remain the only harness. There is no experiment-specific controller.

| Role | Behavior | Optional analytical tools |
|---|---|---|
| Perception | Form ordered action occurrences from speech over all legal tools; one to four distinct candidates per action, at most eight actions | None |
| Solver | Jointly resolve tools and arguments; candidates are hypotheses, not a hard answer vocabulary; retain final answer authority | None |
| Reviewer | Identify supported omissions, operation/argument confusion or ordering problems; inspect named evidence if useful | Target knowledge lookup; task contract |
| Planner | Choose ACCEPT, REVISE or one available REFRESH_CANDIDATES; optionally resolve a remaining knowledge question first | Target knowledge lookup |

Initial Perception receives no eight-card activation shortlist. The full compact
task contract remains present. Parameter evidence is automatically supplied for
the current Perception candidates when Solver runs. Target lookup makes the
activation store available on demand and can also query the separate parameter
store. Both analytical roles may request up to four named legal tools per lookup,
one value per target, at most four values. Returns retain source and target
identity and explicit missing mappings.

Reviewer may use at most two analytical calls before its final report; Planner
may use at most one before its final action. Either role may use none. A refresh
returns to Perception and then Solver; it consumes the single generation revision
allowance rather than opening an unbounded loop. The current complete hypotheses
replace the operative candidate state while previous states remain traceable.
Already visible parameter values are not inserted again, and newly admitted
candidates receive their corresponding values.

No public domain is a hard filter. No knowledge value proves that an action or
argument was spoken. No ASR tool, new acoustic observation, corrective memory or
alternate answering model is added in this version. Additional tools remain
future components to admit from a named failure after this comparison.

The ACCEPT path has four core generations and no mandatory analytical call. The
maximum path has two visits of Perception1 + Solver1 + Reviewer3 + Planner2, or
14 core generations. Only Solver delivers the answer; finite exhaustion keeps
the latest complete Solver answer or the registered abstention when none exists.

## Prospective execution after owner resume

The pair remains model-free-check with only structural check allowed. It has no
ExecutionPlan, launch identities, live/native fit configuration or contact
authority. Registered scorer IDs are retained to define the intended scoring
behavior; the held stages do not execute scoring.

After an explicit owner resume, the registered SLURP broad/factored TRAIN-A run
still goes first. Root then admits this pair only after code/config freeze,
scientific review, budget and exposure registration, correct service identity and
exclusive lease. All4000 packet bindings and source releases must validate before
contact. No retrieval encoder or replacement audio feature preparation is needed.

Use the proposed common decoder-only geometry: three slots, 32,768 context tokens
per slot, 2,048 output tokens and the existing 4/3 prompt-fit margin. Direct needs
the shared whole-roster live fit; the native system needs actual per-contact fit
covering returned tools and refreshed histories. No capacity pass is claimed.
A failed fit stops the comparison before the offending request; it does not
authorize truncation, a service change, silent replay or a new attempt.

The draft ceiling is 4,000 direct plus 56,000 system core generations; 12,001
direct plus 224,000 native fit endpoint calls; and at most 24,000 system analytical
tool calls. These are upper bounds, not contact targets. The draft GPU ceiling is
72 hours including fit and the speech accounting ceiling is 400,000 seconds.
No recovery is included in these draft counts. Formal admission must bind the
structured plans and actual fit registration; no numeric ceiling here lifts the
owner hold.

Generate the two arms sequentially in one root-managed service process. Existing
full scoring may overlap a subsequent qualified arm. No partial outcome inspection
or speculative extra run keeps the GPU busy. A crash pauses dispatch and preserves
all contacts; recovery requires the existing named-failure procedure.

## Analysis and optimization workspace

Keep the prior primary exact-match definition, published-headroom threshold,
paired whole-query-cluster bootstrap (10,000, seed20260914), natural and equal-tier
weightings, and equal-domain sensitivity. Tool accuracy and macro parameter F1
point differences must remain nonnegative for a promising system; those point
guards are not noninferiority claims. Replicate on the same roster before adopting
a stable base. Preserve the historical failed verdict.

The new source reader distinguishes initial, every attempted and operative
Perception states. Candidate inclusion is joined only after both fresh manifests
and first official scores seal. Report primary-target membership across actions,
first-action versus later-only membership, ordered action-occurrence coverage,
actual candidate width, final legal answers outside candidates, and conditional
resolution alongside unconditional full4000 performance. Do not drop unavailable
sources or identify the last attempted refresh as the delivered answer's source.

Report corrections and new errors, exact-call and tool metrics, parameter metrics,
all tiers/domains, parse and finite failures, defaults and unsupported values,
OBS/ORG/SUPPLY/USE, input size, generation/tool contacts and time. Tool use and
refresh subgroups are observational and cannot establish causal benefit. Coverage
95% remains a development priority while full-task system quality also improves.

The resulting optimization workspace exposes candidate hypotheses, named
knowledge queries, review findings, refresh/revision/accept decisions and
source-bound delivery trajectories. This is an engineering substrate for future
trajectory sampling and training-free policy optimization. It is not itself an
RL algorithm, and the current work does not establish stable task gains.
