# Audio2Tool scope-tools np2 feasibility proof

This successor is a CPU-only configuration feasibility check after the registered np3 system arm failed before an attempt or model contact. The named failure is request-capacity provisioning: the system perception prompt required 34,868 tokens while each np3 slot provided 32,768 tokens. No task outcome exists.

The repository already provides `q4km-mmproj-free-a2t-native-role-np2-max2048-v1`. It keeps the total context at 98,304 tokens and the completion ceiling at 2,048 tokens while changing the slot count from three to two, which provides 49,152 context tokens per slot. Its service identity for any future root-owned proof is `serving-a2t-native-role-scope-tools-np2-max2048-v1`.

The feasibility configuration clones both experiments and both baseline fragments. Each baseline clone changes the shared geometry fields consistently: `serving_geometry.slots` and `serving_slots` change from 3 to 2, while `serving_geometry.slot_tokens` and `serving_slot_tokens` change from 32,768 to 49,152. Each clone also opts into the shared `context_budget_limits` mapping with a 49,152-token slot and the unchanged 8,192-token operational reserve. Each experiment clone points to its matching baseline clone and the existing np2 model fragment, names the matching np2 service session, permits `check` only, and remains held. Prompts, knowledge stores, roles, phase programs, speech packets, roster, decoding parameters, run budgets, analysis recipe, and task behavior are unchanged. These fragments do not register a model contact, fit, generation, score, service launch, or campaign.

The shared context-budget rail preserves its historical 32,768-token slot and canonical receipt when the mapping is absent. An explicit mapping must equal the adapter's serving slot, cannot exceed the GGUF-declared 65,536-token context, cannot lower the 8,192-token reserve, and retains the 4/3 headroom condition. Flight preflight runs the existing request-fit verification seam before applying this coarse context check; whenever a fit binding is declared, it remains mandatory. The shared campaign must still fit every realized request before dispatch. Coarse admission never replaces actual request fitting.

Before any full flight, root should register one paired four-row engineering proof through the existing shared flight and lease interfaces. The proof should use the same four frozen roster rows for direct and system, include the current worst-case representative row `tier1_direct:000003`, fit every realized request before dispatch, retain every existing prompt, knowledge, role, phase, speech, and decoding binding, and use one matching np2 resident service. Root must assign the other three rows, unique proof run and attempt IDs, exact contact and fit caps, exposure rows, admission, and source freeze. The proof stops after structural sealing; it creates no authority for a full flight or automatic retry.
