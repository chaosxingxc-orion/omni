## 四、八卡供给与可靠运行

四个 TP2 服务覆盖全部八卡。当前 A0 声明 96 个逻辑槽位，但实际 HTTP 调用受默认线程池约 32 workers 限制，端点没有等待请求。并发执行器修复已通过 110 项针对性测试；正在运行的 A0 保持启动时源码，后继 Fold A 使用修复后的版本。是否提高实机吞吐必须靠后继的逐卡利用率、有效样本/分钟和成本验证。

后台队列顺序：A0 campaign → N1 → 补充诊断 → paired read → Fold A CPU 编码 → 检索准备 → comparator → agreement/held 评估准备 → 独立准入/供给 → 完整 Fold A campaign。最后一项是真实 NPU 推理入口，其余准备条目不能当作 NPU 任务库存。编码仍有全局租约和分析依赖，准备阶段可能出现卡等待；资源隔离和提前准备尚未完成。

SSH 只负责控制和观察，断线不会自动取消后台任务。runner 异常退出可由 guardian 接管持久化队列；恢复先核对进程与终态，避免重复派发。worker 崩溃后的逐样本自动恢复、节点重启后的系统服务恢复仍需落地，不能声称全部故障已经覆盖。不能因 SSH 超时直接重放模型请求，也不能把“保留失败证据”当作不恢复实验的理由。
