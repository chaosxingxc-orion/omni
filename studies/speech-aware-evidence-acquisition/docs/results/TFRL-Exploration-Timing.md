# TFRL探索耗时拆解

## 当前结论

B候选80条配对实验的终态归档包含80条完整样本。主要等待来自执行槽位排队和HTTP请求阶段；当前数据不支持把全量音频预加载作为本轮优先优化项。来源归档SHA `b1be9dfdcba099d3bcf3c5f80cf47e776715bc449249c57b2f4140dd7bbced41`，固定镜像离线分析退出0，与开发机汇总完全一致，无新增模型调用。

| 阶段 | 80条完整样本平均秒/条 | 解释 |
|---|---:|---|
| 执行槽位等待 | 508.571 | `dispatch_trajectory_slot_wait`，代码对应首次请求前等待`slots.get()`；与准备数据不同 |
| HTTP请求合计 | 631.438 | 一条共享P与三路Solver，共四次；包含服务端排队/推理及网络等 |
| 请求渲染合计 | 1.249 | 同一请求可能包含多次渲染，不能当唯一请求数 |
| 原生FIT | 0.902 | 本地actor的容量/来源检查，含其子阶段 |
| 上下文构建 | 0.528 | 只统计记录完成的span |
| CPU执行器等待 | 0.230 | 与轨迹槽位排队是不同层级 |
| 音频文件读取 | 0.019 | 多次读累计，并不证明没有重复读取 |
| 音频base64编码 | 0.002 | 多次编码累计 |
| checkpoint写入合计 | 0.015 | 已完成行落盘 |

各行含嵌套span，不能简单相加为总耗时；不同样本并行，不能将累计HTTP时间当墙钟时间。本次归档时生成和评分进程均已退出0，80条均完成；通用归档工具仍不声明跨成员原子快照。本页已用完整结果原位替换中途68条统计。

完整80/80的campaign耗时2041.22秒，25.52秒/完整配对样本；生成容器2117.95秒，26.47秒/条；样本准入到完成平均1146.28秒、p95 1726.23秒。吞吐用于总任务进度，单样本延迟包含排队，两者不可混用。`admission_wait`平均1.49秒并不代表首次模型请求只等了1.49秒，后续还有轨迹执行槽位等待。

## 优化决策

1. 优先补候选供给，利用当前空闲的另一TP2通道；这是实际资源缺口，无须等待新缓存功能。
2. 不因槽位等待长就直接扩大并发。当前客户端32、服务profile为s48；HTTP阶段本身也有队列，升并发可能只把等待移到服务端。后续在相同固定真实样本上比较吞吐和尾延迟，单列工程配置实验。
3. 960次音频读/渲染事件说明存在可消除的重复工作，但记录中所有音频读总计仅1.515秒、编码0.181秒。可作为低优先CPU优化，不能声称能带来数量级加速。
4. HTTP open-to-headers与请求总耗时几乎相等，但这不区分服务端排队、prefill、decode。缺少同一request的服务端指标时，不将这部分全部归因于模型思考或网络。
5. 保留感知thinking开关等科学配置身份，不能在同一个已启动配对任务中热改；相关消融属于独立后继任务。
