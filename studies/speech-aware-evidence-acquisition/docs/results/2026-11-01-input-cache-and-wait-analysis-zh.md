# 输入缓存与准入等待分析

## 结论

全量真实音频预加载到181主存可行，固定输入应跨实验共享。更有价值的缓存层是解码/预处理结果和模型音频编码结果，但当前“准入→P请求”281.82秒不能当作数据加载时间。既有完整500条计时表明，客户端音频读入和base64编码仅0.018秒/条；优先排查槽位等待和串行FIT，避免花大量工程时间优化小项。

本次没有重新抽样、制作数据集、调用模型或tokenizer，也没有改变服务配置。缓存实验仍使用已固定REAL500/construction625名单。

## 实测量级

以当前选用的2×TP4-S128完整500条为准，正式容器读取原阶段日志并关联完整checkpoint，500条均有计时，分析退出0。

| 项目 | 每条平均秒 | 解释 |
| --- | ---: | --- |
| 准入到P请求 | 281.815 | 已拆成FIT前、FIT内、发送前互斥区间；FIT前内部仍待细分 |
| 客户端音频读取/base64 | 0.018 | P/S与FIT相关读入累计；不含服务端音频解码/编码器 |
| 上下文构造 | 0.564 | 全样本轨迹累计 |
| 请求渲染 | 0.694 | 包含嵌套工作，不能与音频项直接相加 |
| FIT | 18.492 | 包含FIT锁等待、渲染、服务测量和记录，不等于tokenizer纯计算 |
| P/S HTTP请求 | 470.182 | 含网络、服务排队、音频编码、prefill与decode，尚不能独立归因 |

500条音频读入/编码事件累计9.02秒，是并发事件时间之和，并非整机可节约墙钟。整批生成封存1383.15秒，不能把281.82×500作为可消除的实验耗时，也不能承诺缓存会实现数量级提速。

## “准入”实际含义

运行器先创建样本协程并记录admitted_ns，再等待primary_slot中的slots.get。默认路径取得的槽位直到整条轨迹结束才释放，P完成后的CPU上下文准备、FIT和S调用均占用该槽位。因此已准入样本仍可能在等待前面的样本完成。线程池宽度与槽位数相同，过量协程入队不增加NPU并发。

native FIT在fit_lock内完成请求渲染、计数服务调用及凭证制作，锁覆盖网络等待。相邻样本竞争该锁会放大尾延迟；仅预读音频不会消除这类等待。还需补齐槽位、线程池、FIT锁和FIT服务的独立计时，才能量化可优化份额。子智能体已完成同样本、实际P请求ID、嵌套FIT事件的逐条关联，500条全部唯一匹配，结果如下。

## 子智能体等待归因结果

以下三个区间不重叠，可以相加；所有样本在6.220秒内被客户端准入，记录槽位256、队列深度1024。

| 区间，平均秒/条 | 全500条 | 首256条 | 后244条 |
| --- | ---: | ---: | ---: |
| 准入→P FIT入口 | 264.938 | 42.408 | 498.412 |
| P FIT入口→出口 | 16.872 | 32.152 | 0.840 |
| FIT出口→P请求 | 0.006 | 0.006 | 0.007 |
| 合计 | 281.815 | 74.565 | 499.258 |

后244条P FIT开始时间按顺序与最早244个样本完成时间比较，平均仅落后0.213秒，p95为0.468秒。这与“整条轨迹占用槽位，完成才释放”源码一致，强烈支持后批主要等待槽位释放；没有直接槽位时间戳，不能将每毫秒残差都精确标为槽位等待。

P FIT中渲染前区间平均16.583秒，渲染开始到FIT结束仅0.289秒；首批分别31.876秒与0.276秒。长FIT计时主要发生在渲染前，与锁竞争吻合，但该区间还含验证/租约工作，不是纯锁等待的直接测量。当前GuardedTokenizer共享client/counters/contact_sink，不能简单删除锁；新RecoverableNativeFitGate也包了整次调用锁，优化时必须一起缩小，否则内层并发仍被外层串行化。

首批进入FIT前平均42.408秒仍有未归因部分：P上下文构造本身仅0.001467秒/条；首个FIT在最后一个P上下文完成后17.398秒才开始。工作流初始化、事件循环、线程启动和请求准备是候选原因，需要边界计时或短CPU剖析确认，不能断言这42秒全部可消除。

先让P开始不一定缩短全任务完成时间：把排队从客户端移到vLLM并没有消除工作量。验收应以完整数据集耗时、有效吞吐、逐卡利用率和精度为准，而非只降低“准入→P”这个指标。后续优先采用准备队列→就绪请求队列→模型槽位，并保留S/裁决继续执行的公平性和前缀局部性。

## 缓存容量与层次

只读统计既有元数据对应文件大小，未读取答案或重算音频哈希：train 50627条压缩音频2.741GB，devel 8690条0.470GB，test 13078条0.700GB，合计约3.911GB。construction625为55.061MB。181当次可用主存约2.012TB；容量足以预加载原始音频，但解码波形、特征和编码结果要另计。

以625条2726.847秒音频估算，16kHz单声道float32波形约174.5MB，不含容器对象、padding及额外副本。128维mel、hop160的float32特征约139.6MB，仅为未padding近似。应测实际张量字节数再定缓存容量，不能用压缩音频大小代替特征内存。

| 层次 | 复用内容 | 实现建议 |
| --- | --- | --- |
| 主机文件缓存 | 固定音频、元数据、向量/索引 | 优先OS页缓存或共享mmap，避免每进程复制整个数据集；按现有固定版本预取 |
| CPU预处理缓存 | 解码波形、重采样、mel等 | 绑定音频摘要、处理器版本和参数，跨轮次共享；不缓存动态答案 |
| 引擎编码结果缓存 | 音频编码器输出 | 主存保存较大工作集、NPU保存热点，容量受控，记录命中/淘汰和传输量 |
| Transformer前缀缓存 | 完全相同前缀对应KV | 沿用自然前缀匹配；不同上下文后缀不能当成同一KV |

当前服务使用mm_processor_cache_type=shm，镜像默认预算4GiB（启动命令无覆盖），因此并非没有多模态缓存。SHM预处理缓存不等同于编码器输出缓存，更不等同于完整请求结果缓存。本次一次只读metrics快照，两实例累计多模态缓存命中5328/7395，约72.05%；这是服务生命周期跨实验累计值，不是REAL500独立命中率，也不是编码器输出命中率。两端当时running/waiting均0，当前没有生成请求在处理。

当前Ascend镜像还包含ScoreEncoderCacheManager及CPU/NPU两级编码结果缓存、固定页内存和异步拷贝路径；当前启动命令未配置该自定义管理器。可作为候选，不应直接认定适用于本模型或能提速。示例候选入口为 `--ec-manager-config`，管理器类 `vllm_ascend.ec_manager.score_ec_manager.ScoreEncoderCacheManager`；容量单位为embedding slots，不是样本数，默认100000 slots也不意味着能容纳整个数据集。

Qwen3-Omni当前音频路径接收input_features并调用audio_tower。通用enable_mm_embeds开关不证明该模型支持直接上传预计算音频embedding；应优先验证已有引擎缓存路径，而非绕过模型输入协议。

## 优先改进与验证

1. 补齐互斥等待区间：排入样本队列、取得槽位、提交线程池、线程开始、FIT锁取得、FIT服务开始/结束、P发送。保持约600秒汇总，无高频模型监控。
2. 将不依赖前序模型输出的P上下文与FIT提前准备，生成槽位仅承载已准备好的调用；S和裁决依赖真实P/候选输出，只能流水线提前，不能伪造预计算。复用现有node_pipeline设计时先检查语义与恢复行为。
3. FIT改为有界并发：计数/去重/凭证发布保留原子性，网络调用移出全局锁；不能直接删除锁而破坏预算。分别观察锁等待、服务耗时和NPU吞吐。
4. 用固定数据版本做主存预加载；热缓存不能掩盖首次读取成本。优先统计既有SHM缓存命中与淘汰，确有容量不足再扩容。
5. 对CPU/NPU编码缓存做一次受控配对验证，沿用固定真实名单、相同上下文、推理预算和8卡资源。冷启动/构建耗时、热运行耗时、encoder执行次数、H2D字节、KV占用、吞吐、精度和重启恢复分别汇报。有收益才部署，未测量前不宣称提速。

主存缓存可服务多实验，但当前引擎内缓存通常属于服务实例，不能假设两个TP4实例或服务重启后自动共享。持久化的是稳定输入和可重建缓存索引；生成结果依旧按科学实验和恢复尝试管理。


## 最小工程改造与交付边界

已核查当前 `core/preparation_fit.py` 与 `core/native_fit_recovery.py`：内层FIT将同一个GuardedTokenizer的client、counts、contact_sink串行复用；恢复包装器还依赖调用前后receipts列表长度提取当前请求收据。这两处都必须改为逐请求归属，才能安全并发。只移除任一锁均不可作为优化方案。

第一步补齐两层锁的独立等待事件：`native_fit_lock_wait` 和 `native_fit_recovery_lock_wait`。事件绑定sample_id/request_id，只测取得锁前的等待，不包含锁内网络或写盘时间；默认关闭，不改变请求和锁语义。写日志失败必须释放已经取得的锁并传播错误，避免观测工具自己造成死锁。它提供后续受控优化的测量基础，本身不带来吞吐收益。计时已由隔离工作树审阅合入实现树 `6a5380d4`，同步公开仓代码 `ecad7b70`；npu2固定saea-base镜像、关闭网络的CPU定向测试49项通过，11.33秒，退出0。测试覆盖原生FIT、恢复和计时失败释放锁；公开仓因原有测试集合差异为46项通过，9.10秒，退出0。使用模拟端点，无真实模型/tokenizer调用，尚未部署到真实任务；并发化与缓存收益仍未实现或验证。

后续按下列边界实施，不重开推理引擎配置搜索：

| 阶段 | 具体修改 | 验收与限制 |
| --- | --- | --- |
| FIT逐请求状态 | 每个contact持有独立client、counter、sink和receipt；共享短锁只预约contact ID、每样本额度和总端点预算 | 重复ID/并发超预算必须在HTTP前拒绝；未知结果保留预算预约和journal，不能自动归还后重发 |
| 有界FIT并发 | 预约成功后在独立有界执行池做render/HTTP/凭证落盘；完成后短锁发布结果；恢复wrapper按contact取receipt，不再切片共享列表 | 同时改内外两层锁；记录实际消耗、未使用预约、未知消耗；不因并发造成跨样本凭证关联 |
| 准备与生成分离 | 固定首P输入提前进入CPU/FIT准备队列；准备完成才申请生成槽；当前P之后的S与裁决按依赖实时准备 | 不缓存历史P答案；保持精确FIT输入校验；实现有界背压，防止占满主存或向引擎转移无界排队 |
| 接续公平调度 | 预留继续执行能力给S/裁决，保留实例亲和性；测量之后再决定是否改为每contact释放槽 | 取消时仍等待已发送调用终态，不提前释放正在运行的槽；不承诺仅提前P就缩短全任务 |
| 缓存复用 | 共享固定数据文件/索引；先验证现有SHM命中和淘汰，再测模型支持的encoder缓存 | 以完整任务墙钟和质量为准；冷启动成本、热缓存收益分报，不挤占KV而降低有效并发 |

部署验证沿用同一固定真实名单与2×TP4-S128。先完成并发预算、重复请求、异常、取消和恢复的模型免费测试，再在下一已授权真实任务采集新增事件，报告处理条数/总数、完整耗时、秒/条、8卡与2实例、token和失败消耗、ETA。正式质量指标继续由官方评分器汇总。样本级等待事件正常写入本地日志，主控只约600秒或终态读取汇总；不增加高频模型监控。

## 有界FIT并发实现

当前实现已将raw-vLLM FIT从整调用全局锁改为默认最多8个并发请求。每个contact独占client、counter、sink与收据；短锁预约样本/端点预算并发布结果，失败或未知请求保留预约，不能换ID重发规避预算。恢复包装器按contact获取收据，不再依赖共享列表切片；两层锁均已缩短。特征包多端点路径仍保持串行，避免破坏其连续日志验证。

隔离实现101项定向测试通过，25.68秒，退出0；公开仓联合候选池及恢复凭证测试107项通过，32.04秒，退出0，覆盖并发端点、样本额度、重复、未知响应、恢复收据和既有登记约束。这是并发能力与正确性证据，真实完整任务提速尚未测量；CPU准备仍在轨迹槽内部，后续需分离就绪队列，不能声称已消除全部等待。
