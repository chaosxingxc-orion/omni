# 预检重复校验权重：原因与修复

更新：2026-11-01。本文记录 CPU 工程问题，不代表模型精度或 TFRL 收益。

## 实际证据

最终单步学习任务在首次生成前运行约4分35秒，CPU约95.5%。主线程读取的 `/proc/<pid>/io` 中 `rchar=215541391320`，同时文件描述符指向第6个 safetensors 分片。该计数包含进程全部读取，不能直接当作磁盘读取量；`read_bytes=0` 说明这些读取未在该进程上产生相应块设备读计量。已知模型约60GB，证据符合重复从页缓存读取并计算哈希，不足以单凭计数给出精确遍数或加速倍数。

## 原因

vLLM gate 复用 `contracts/gate_runtime_gguf.py::_verify_gguf_files`。首次全量校验后记录 `_SESSION_FULL_HASH_DONE`，后续调用却仍依赖模型根目录下的 `.saea-runtime-identity-cache.json`。实验将共享根只读挂载；最佳努力写缓存失败被正常忽略。实际磁盘缓存收据哈希一致，但记录旧设备号49，当前重启后为48；每项统计身份失配，加上无法刷新，导致每次 gate 再次计算完整权重 SHA256。缓存缺失或属于旧收据时也有同类问题。

这条路径和 `verify_model_directory` 的目录集合检查不同；后者只检查文件集合。此次修复不跳过运行库、源码树、进程身份或样本 FIT 校验。

## 实现

在同一解释器内保存实际成功全量校验的记录，以 PID、规范化模型根、runtime receipt SHA256 绑定。磁盘缓存自身未变化时，优先复用该记录，覆盖缺失、旧收据和同收据旧设备号缓存；每个文件仍检查 device、inode、size、mtime 和 ctime。哈希前后元数据变化立即拒绝，只有全部文件及总大小通过才发布缓存。

默认新进程、新根、新收据仍须全量校验；fork 清空缓存及继承锁状态。显式 `full_hash=True` 始终重算。显式快速模式保留原有语义，磁盘快路径结果不会被提升成新的完整字节校验证据。新增诊断 `gguf_files_memory_cache_hits` 可区分真实复用。

磁盘缓存原有统计身份威胁模型保持；本地缓存额外使用 ctime，但仍不能对抗能维持全部元数据的特权内容修改，也不声称只读客户端挂载意味着底层分布式文件不可修改。

## 验证和部署边界

固定 saea 镜像 CPU 测试覆盖：只读写失败、多 gate 复用、旧磁盘缓存、磁盘缓存变化、mtime/ctime/inode/size 漂移、哈希中变更、PID/真实 fork、模型根与收据变化、强制全量和新进程校验。原有 identity-fastpath 合约同时回归；父线程补充同收据旧设备号回归后，缓存与封存恢复相关测试合计 **43项通过，4.43秒**。进程内 ctime 变化会拒绝旧内容；显式快速模式在新进程仅使用磁盘缓存时仍保留已声明的弱保证。

部署前后的实际权重读取量、首次预检及后续 gate 秒数仍需由主线程测量；当前只证明未变化的小型文件多次打开从重复哈希变为一次哈希，不能据此预报整项实验加速倍数。实现未改运行中的固定执行树，需后继执行树部署。
