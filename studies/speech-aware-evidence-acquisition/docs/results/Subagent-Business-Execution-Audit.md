## 已定位原因与修复状态

1. **旧会话追加任务未产生新业务。** 两个历史会话返回旧任务确认，新 TASK 目录没有新 receipt；新会话读取同一文件后产生实物。已采用任务文件接续。平台内部消息路由不可见，不能宣称已经定位或修复平台根因。
2. **权限边界发生在容器产物读取。** Reflexion 固定镜像以 root 写 mode0600 文件，宿主复制报 Permission denied；负责人仅调整独占产物目录 owner 后成功回收。这不是缺少子智能体写授权。后续应在固定启动配置中统一产物 UID/GID；通用自动化尚未验收。
3. **运行前验证未覆盖真实数据流。** 发布名单按目标/边界/控制拼接，runtime 按 sample_id 排序，首请求前失败。现已统一配置顺序并提前拒绝不规范名单；主线程固定镜像60项回归通过。保持名单集合与原候选不变。
4. **恢复遗漏旧租约交接。** 首次异常正确保留租约，但接续未先证明旧进程与请求结束，再次被拒绝。已核对 PID、容器终态、连接、引擎请求计数和 journal，保留 guard 与原 metadata 后交接。11:56已获得TP4的32条请求意图/17份响应，以及双卡任务45条意图/13份响应；随后检查点校验分别1/80和0/80。恢复成立，科学结果仍未完成。
5. **验收协议未被严格执行。** Reflexion 有代码与报告，但 result 使用了自定义状态和 artifacts 字典，已有验收器拒绝。已打回同一负责人，但原会话再次只确认旧报告、未修改文件；新接续负责人读取相同文件后完成修复，主线程复核38个哈希通过。主线程未代填。业务报告的结论与机器可读交付格式都要完整。
6. **重复准备仍有偏差。** 恢复负责人在被要求复用已准备运行并创建新 attempt 后，仍创建 v3 树和重新准备。已要求解释必要性；未核实前不称此问题已修复，不再打断当前运行。

## 固定执行与验收方式

沿用 `scripts/analysis/verify_agent_delivery.py`，不另造一套监控系统。任务文件固定目标、输入、输出、依赖、资源边界及验收命令；子智能体先写 TASK SHA 回执，再实施，最后交付 REPORT 和文件哈希。

启动后首先核验接单及第一份业务产物；中途主要读取文件或终态事件，正常实验观察间隔约600秒。无 receipt、旧 TASK 哈希、仍在实施、程序失败、语义拒绝分别处理。通信超时先查目录与进程，绝不直接重复 API 或 NPU 请求。

交付顺序为：任务身份正确 → 文件完整与哈希通过 → 必要测试 → 实际业务结果 → 科研结论。NPU 任务至少需要真实请求/响应或检查点，收益必须有完整配对评分；“进程启动”“测试通过”“候选编译”各自只证明对应阶段。

原负责人修正不合格交付；只有确认旧会话未执行新任务且没有活跃副作用，才用新会话读取相同文件接续，禁止反复发送长提示或主线程默默接管全部实现。
