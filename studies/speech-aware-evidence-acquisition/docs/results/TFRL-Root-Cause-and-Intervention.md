# TFRL 错误根因与节点干预方案

## 分析原则

先区分程序性错误与系统原生错误。程序性错误是实现、接口或配置违反约定，修复共享工程基座并用测试锁定，不计作算法收益。系统按预期运行但任务仍答错，才进入数据质量与系统节点优化。每个案例分别记录表现、证据、根因假设和干预结果；证据不足时保留“未定位”，不靠模型自述认定原因。

## 第一层：程序是否正确执行

核对请求参数是否按配置发送、reasoning与最终输出预算是否正确划分、停止原因、结构化输出是否真正到达引擎、响应解析是否损失内容、上下文是否被错误截断、知识及版本是否装载正确、路由和评分是否一致。

| 已有现象 | 目前证据 | 应先做的验证 |
| --- | --- | --- |
| Reflexion内容超长 | 内容299字符，应用上限200字符 | 这是应用协议拒绝，不是上下文或输出token不足。明确合理长度契约，核查提示与验证器一致性；增加引擎输出预算不会改变字符上限。 |
| ACE JSON截断 | finish_reason=length，4096 completion中3093用于reasoning | 配置容量不足是直接候选根因。先在相同输入与协议下增加最终输出配额或降低reasoning占额，再单独对比短引用；不要同时改多项后归因。 |
| JSON缺外层字段 | 现有响应是完整可解析JSON；非空提示例子仅展示内层 | 缺字段不能直接认定输出预算不足。逐请求核验stop/length及原始请求，分别测试更充足预算、完整契约提示、引擎结构化输出；目前只完成提示版本化，未证明根因已消除。 |
| 协议合法却有错误规则 | TRAIN参考直接反驳删news_topic/song_name建议 | 格式检查没有证明语义，转入知识构建分析；不是放宽解析器能解决的问题。 |

引擎配置是可调整的工程组成部分。对于明确截断，预算对照优先；response_format/JSON schema必须验证当前引擎、thinking和共享请求桥支持，不能把提示中的JSON示例说成约束解码。只有实际配置未按约定生效才定为bug；资源预算与输出需求不匹配先归为配置设计问题，不冒充算法劣势。

## 第二层：数据自身是否成立

检查音频是否可辨、转写是否一致、意图和槽位标注是否自洽、边界与类型是否符合原始定义、同类样本标注是否冲突，以及是否存在多种合理答案。不能把不符合常识的参考直接判错，也不能把官方参考当作无缺陷的真理。

可疑样本进入独立标注审计，保留原标签和官方评分；学习材料中标记争议，暂不从该样本提炼普遍规则。分别汇报原官方口径和经审计的诊断结论，不静默修标签。按真实意图/槽位组合覆盖，不做笛卡尔积。

## 第三层：知识构建与知识消费分开定位

**知识构建链路：** bad case选择 → 预测与参考反馈 → 反思 → 规则整理 → 知识发布。逐步核对输入是否包含关键缺失槽位，反馈是否被读成“高分即正确”，反思是否从减少FP错误推导成删除必需槽位，整理是否丢失条件或引入冲突。已有三条规则与来源参考直接冲突，说明构建产物存在语义问题；尚不能仅凭结果判定发生在反思还是整理，更不能说所有原始任务错误来自知识构建。

**知识消费链路：** 音频感知 → 查询表示 → 检索/排序 → 上下文组装 → Solver槽位提取 → 后处理。按顺序回答：知识库里是否存在所需信息？召回到了吗？排序后仍在吗？实际发送的上下文包含吗？Solver看到了但忽视，还是感知误差导致其无法匹配？最终解析有没有丢掉正确槽位？每一步依赖实际材料与原始响应，不能用最终错答案反推整个链路。

## 最小节点干预矩阵

固定一份TRAIN/开发bad case名单、模型与评分口径，每次只变一个节点并保留完整费用。优先利用已保存P结果和知识供应，在允许的原生复用机制内避免重复感知。

| 干预 | 其他环节固定 | 可以检验的问题 |
| --- | --- | --- |
| 修正已确认的感知错误 | 知识与Solver策略固定 | 感知错误是否足以解释下游失败 |
| 强制提供预先审查的相关知识 | 固定P与Solver | 检索或排序不足是否是主要瓶颈 |
| 只修复一条错误/歧义规则 | 固定P、其他知识及消费策略 | 构建产物错误是否导致失败 |
| 保持完全相同证据，改变Solver指令 | 固定P、检索、知识 | 消费方式是否能正确选择槽位 |
| 比较原始模型内容与最终结构 | 不新增推理 | 后处理/解析是否引入程序性错误 |

金标感知与强制知识只作诊断上界，不计入可部署系统成绩。干预成功说明该节点在受控条件下可修复案例，不自动证明它是唯一根因。对随机生成使用配对重复，汇报repair、break、无变化和不确定性，避免把一次偶然答对当因果证明。

## 案例记录与归因验收

每个案例使用稳定 sample_id，绑定数据版本、模型/提示/知识版本、原始请求与响应摘要、评分和费用。逐节点记录实际输入/输出及其哈希；公开报告仅放脱敏汇总。最小记录字段为：`error_class`、`data_audit`、`first_divergent_node`、`evidence_refs`、`intervention`、`paired_outcomes`、`confidence`、`next_action`。

- `error_class`：程序bug、配置设计问题、数据争议、构建问题、消费问题或未定位；允许多个问题共存，区分最早错误与下游放大因素。
- `data_audit`：音频/转写/标签/任务定义分别核验。标签争议保留原官方成绩，禁止将争议样本的规则自动推广。
- `first_divergent_node`：定位到反馈生成、反思、整理、发布、感知、检索、排序、上下文、Solver或解析；没有中间证据就标未知。
- `intervention`：固定其他节点，注明替换的唯一变量、旧新配置及可执行复现入口。依赖多节点联动才修复时，追加组合干预，不强行归为单一原因。
- `paired_outcomes`：原错误修复数、原正确破坏数、净变化、协议通过率、官方指标、tokens与耗时。分开记录工程修复收益和学习收益。

工程bug的验收是失败用例可复现、修复后通过且相关回归不破坏；系统优化的验收是干预有证据、候选可部署、独立开发评估获益。诊断时替换金标不算候选成绩，单次答对也不算稳定提升。测试集只用于冻结方案的最终汇报，不回流本轮诊断学习。

## 各算法当前真正缺口

- TF-GRPO式经验更新：已有候选对照，但未取得稳定开发收益；需识别反馈归因、规则条件及消费命中，不能用部分奖励选择替代可迁移证据。
- ACE：顺序反思/整理链路已实现，当前先解决预算/协议契约；之后逐节点检查反思和整理哪一步制造错误、冲突或丢失条件。
- Reflexion：旧轨迹均早于当前记忆，没有“使用新记忆后重试”的在线因果证据；现状应称离线经验转移，不能宣称已实现完整的自纠错循环。
- GEPA：固定16条仅验证原生机制，模板未学习；父子配对组件已实现，但真实反馈→mutation→配对选择→下轮使用尚未闭环。

下一步先修程序和配置问题；随后按数据质量、构建节点、消费节点做受控诊断，再决定优化哪个算法部件。静态规则准入仅防止已知错误传播，不能替代这些实验，也不等同于精度提升。
