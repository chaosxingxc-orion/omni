# 两次主机故障：推理引擎、业务触发与 Ceph 内核缺陷的因果分析

核查：2026-11-01。**当前最强解释是业务侧并发持久化触发了旧 Ceph 客户端的已知空指针竞态。已找到与故障指令直接对应的上游修复；没有证据支持“特定音频样本触发 vLLM 生成算子 bug”作为第二次故障的直接原因。** 触发负载和底层缺陷是两个层面，业务代码仍需改善持久化效率与诊断能力。

## 可以确认的故障位置

两次故障分别在10月31日10:23:49 UTC、11月1日05:01:13 UTC，均为`unsafe_request_wait+0x1d0/0x564 [ceph]`访问空地址`0x8`，调用路径为`fsync → ceph_fsync → unsafe_request_wait`。第二次随后Ceph工作线程自旋锁等待超过26/48秒。它们是内核Oops与主机锁死，不是目前已取得的用户态vLLM core文件；仍无vmcore。

实际安装的`linux-image`和`linux-modules`版本均为`5.15.0-25.25`。只读检查当前加载模块与磁盘模块的`srcversion`一致。磁盘`ceph.ko` SHA256为`42476bf3e27b084b1d495be72e2bf1721b7ab2d6ee70f7089d6fc092e012b955`。对该二进制反汇编得到：

```text
unsafe_request_wait+0x1cc: ldr x0, [x26, #832]
unsafe_request_wait+0x1d0: ldr w2, [x0, #8]
```

第二条就是两次日志中的故障指令；中间没有空指针检查。结合上游相同循环结构，这对应读取`req->r_session`后直接访问`s->s_mds`。该循环位于`i_unsafe_dirops`处理分支，支持目录元数据同步相关竞态判断；没有用户态文件描述符/线程栈，尚不能指出是哪一个具体业务文件。

## 对推理引擎假设的检验

| 证据 | 观察 | 含义及限制 |
| --- | --- | --- |
| 第二次故障CPU | CPU200；学习启动器CPUSET为192–207 | 与学习客户端运行范围一致 |
| vLLM容器CPU绑定 | 两个实例分别128–159、64–95 | 均不含CPU200，削弱vLLM进程直接发出该fsync的解释；检查的是保留容器配置，不是完整历史调度轨迹 |
| 05:00:54–05:02:10服务日志 | 实例0共64条、实例1共65条，全部为`GET /v1/models`成功；`POST /v1/chat/completions`和ERROR均0 | 该窗口没有生成完成的服务日志；单凭访问日志不能排除未完成请求，但与下项共同判断 |
| 中断恢复attempt | 新原生请求意图0、响应0；桥接46个意图、43个复用响应 | 故障发生在历史响应回放与持久化阶段，没有新音频/提示交给生成接口的证据 |
| 故障前写入密度 | 05:01:12桥接157份、learner81份JSON；05:01:13另48和26份 | 文件mtime表明元数据操作集中爆发，不等价于精确syscall计数 |
| 持久化代码 | `publish_new`每份文件写入后fsync，再链接发布并fsync目录；学习使用ThreadPoolExecutor | 大量回放也会产生密集文件/目录同步，无须新模型计算即可触发文件系统竞态 |

**纠正一个容易误判的点：** 内核Oops中的`PID`可以是线程TID。第二次117680不同于学习主进程112315，并不能证明它属于另一个进程；它可能是学习线程。重启已丢失`/proc/<tgid>/task/<tid>`映射，按该PID查询持久journal无业务条目，因此目前只能说CPU范围和工作阶段高度吻合，不能宣称线程归属已最终证明。第一次22573的业务归属仍不明确。

因此，数据规模、并发回放、创建/链接/删除小文件与目录fsync的时序可能是触发条件；并不需要某条语音或文本内容异常。尚不能绝对排除其他用户态程序、MDS会话变化或驱动内存损坏的间接影响，但现有证据无需依赖这些假设就能解释直接空指针路径。

## 对应的上游修复

1. **首要核查：[7acae6183cf3](https://github.com/torvalds/linux/commit/7acae6183cf37c48b8da48bbbdb78820fb3913f3)，2022-04-14，`ceph: fix possible NULL pointer dereference for req->r_session`。** 提交说明指出请求先进入`i_unsafe_dirops`，随后才赋值`r_session`，可因此空指针。修复在两个遍历分支加入`if (!s) continue;`。当前模块故障点明确缺少这项防护，且故障地址/指令吻合。上游关联[Ceph #55327](https://tracker.ceph.com/issues/55327)。这是与当前故障高度对应的已知缺陷，不再只是看到Ceph栈的泛化推测。
2. **一并核查：[5bd76b8de5b7](https://github.com/torvalds/linux/commit/5bd76b8de5b74fa941a6eafee87728a0fe072267)，2022-11-10，`ceph: fix NULL pointer dereference for req->r_session`。** 请求转发或重发会改变`r_session`，修复引入`mdsc->mutex`保护。不能仅补空值检查就假定同一类会话竞态全部消失。
3. 先前检索出的[708c87168b61](https://github.com/torvalds/linux/commit/708c87168b6121abc74b2a57d0c498baaf70cbea)是边界条件`>`改`>=`；当前二进制已有`b.cs`的无符号`>=`检查，不应把它误报为本次首选修复。[89d43d0551a8](https://github.com/torvalds/linux/commit/89d43d0551a848e70e63d9ba11534aaeabc82443)处理分配失败与零会话数，也不是已观察到的`r_session == NULL`指令的直接防护。

未取得历史vmcore或发行版完整源码/回溯验证，不宣称唯一根因已排尽，也不指定未经Ascend支持矩阵核查的升级包版本。已检查的是当前仍在使用的同版本模块，不能用它代替历史内存转储。

## 工程处理与下一步

- 保持已部署的本地持久盘热状态和开发机异步归档；这能移走业务主要Ceph写负载，不能修复旧内核，也不能保护其他仍直接写Ceph的程序。保留fsync与请求意图先落盘的顺序，不以删除可靠性换吞吐。
- 按Ascend驱动/固件支持矩阵选择包含上述修复及后续稳定补丁的受支持内核，由运维安排维护窗口。此次没有升级、重启、卸载或热替换模块。
- 下一执行版本记录`pid`、`threading.get_native_id()`、boot、阶段及输出路径类别；在本地收集fsync次数/时长直方图。共享证据不发布原始提示、音频或主机内部地址。
- 对回放路径优先减少不必要的重复持久化；可考虑追加式日志和批量提交水位，但必须保持每条发送意图已持久化、未知请求不重发、响应来源与全部成本可追溯。并发降低只适合诊断或临时缓解，不能代替内核修复，也不应无依据降低NPU推理并发。
- 若需验证触发条件，在隔离测试环境对比“纯CPU小文件发布/目录fsync”和“同一真实业务输入、本地盘”；先验证内核补丁，禁止在生产181故意重现已知主机崩溃。无须先对全部数据重新rollout。

本轮只进行了日志、容器配置、源码与模块反汇编的只读检查；未发送模型请求、未改变引擎配置、未执行故障压测。原始日志、精确反汇编及上游提交响应保存在私有诊断目录供复核。
