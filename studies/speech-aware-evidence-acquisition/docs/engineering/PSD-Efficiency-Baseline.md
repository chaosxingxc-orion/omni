# P→Slot→Decision 效率基线验收

## 当前状态

效率基线尚未锁定，AI Core >80%尚未实测通过。两实例均为TP4、context65536、max_num_seqs128、max_num_batched_tokens2048、memory utilization0.92，原先服务镜像不同，B已开始配置化切换到A的固定镜像；服务就绪、session身份及完整配置仍须核验，不能据此宣称对齐完成。客户端并发32仅为起点。仅推进P→Slot→Decision，不启动P→Solver。

## 锁定内容

两实例对齐服务镜像、模型/权重/tokenizer、引擎版本、prefix cache策略、TP与批处理参数，并记录实际session身份。锁定业务release及manifest、输入名单和知识快照、客户端并发/准备/校验/预载/ready队列配置，以及detached启动、checkpoint与观察器配置hash。Slot thinking实验变量单独列明，其余工程配置一致。

## 利用率与效率要求

8张卡分别验收AI Core时间平均利用率严格大于80%，不能用8卡总平均掩盖低负载卡。窗口按各实验臂首个生成请求派发至最后生成响应结束计算，包含CPU供给不足产生的空闲及排空尾部；模型加载/首次输入准备单列，同时报告全任务墙钟效率。采用后台约30秒采样，主线程约600秒或终态读取。采样均值属于观测估计，不声称连续每一时刻都超过80%；缺测不能记为0或通过，不得挑选忙碌片段。

除逐卡均值，报告P10、零利用率占比、超过80%的观测比例、采样覆盖，模型running/waiting、ready队列、prefix cache命中、样本完成/总量、秒/条、资源与ETA。逐节点准备/FIT/HTTP/校验和队列等待分别统计，并发嵌套耗时不可相加成墙钟。

## 优化与放行

先提前加载真实输入与知识，CPU准备/评分/分析异步；再以配置上探并发32/64/96/128和准备/校验线程；应用侧供给充足后才调整batch tokens2048/4096/8192。最终选择真实端到端吞吐收益平台，不能以并发数字或单独利用率代替样本效率。复用原Fold A1080和断点，不能用重复合成样本证明基线；禁止为提高利用率缩减必要知识、输出预算或评分分母。

未达到阈值时先归因CPU饥饿、tokenizer/FIT、同步屏障、引擎批处理或解码限制，优化后接续。只有真实PSD输入验证利用率、吞吐、正确性与断点后才标记“效率基线锁定”；当前外部验收策略是待执行要求，不等于运行时强制检查已接通。

## 三段效率分解

统一按实验、attempt、样本、节点、请求关联记录。P、Slot、Decision均重复经历供给→推理→验收；after_model_call还会为下一节点准备知识，不能把整个hook耗时全部计入验收。以下为验收规范，不代表全部埋点已实现或已有实测值。

| 环节 | 分解内容 | 核心指标与瓶颈信号 |
| --- | --- | --- |
| 数据供给 | 音频读取/编码、冻结知识召回/去重、上下文构建、请求渲染、FIT、准备线程排队、ready后等待派发 | 准备完成请求/秒，平均及P50/P95秒/请求，缓存命中率、ready深度；NPU有容量但无ready请求说明供给不足 |
| 模型推理 | 客户端传输、服务端排队、多模态编码、prefill、decode、响应传回 | P/Slot/Decision分别统计请求延迟、输入/输出tokens、生成tokens/秒、running/waiting、prefix命中及逐卡AI Core；HTTP总时长不是纯NPU计算时长 |
| 结果验收 | 校验线程排队、协议解析/合法性检查、结果归并、来源核验、持久化checkpoint；批次封存与官方评分另列 | 验收完成样本/秒、平均及P50/P95延迟、积压数量/最老年龄、fsync耗时、拒绝/异常计数；验收积压且阻塞轨迹准入说明回压 |

供给端和验收端均需区分“等待容量”“等待CPU线程”“实际处理”。FIT可能调用服务端，应按实际执行位置记录，不能默认全部算CPU；模型响应合法性校验和官方正确率评分分开。

### 时间与吞吐口径

每个节点目标记录准备入队、开始准备、ready、dispatch、response、开始验收、验收完成；样本另记提交、准入与最终checkpoint。重试/恢复逐请求计数，不能用最后一次覆盖历史成本。

单次串行请求可由相邻边界得到非重叠区间；真实流水线存在预取和并行分支，三类累计耗时不保证可加成单样本或整批墙钟。报告分别列累计工作时长、排队时长和实际端到端延迟；只有边界齐全且能重建依赖时，才给出关键路径占比，未归因间隙单列，不能硬凑100%。跨主机不直接相减未经校准的时钟。

同时汇报两种效率：①全任务墙钟/终态样本数（吞吐倒数）；②每条样本提交到checkpoint的延迟均值及P50/P95。生成完成、验收完成、成功交付及正式评分数量分别列出，拒绝和失败不从分母中消失。批次封存/评分作为独立CPU队列，报告耗时、积压与ETA，不阻塞下一批推理；节点之间必要的合法性检查仍须完成。

### 现有观测与缺口

已有通用stage timing支持normal/debug配置；debug可记录音频读取/编码、上下文与请求构建、FIT、HTTP、准备/校验容量等待、线程等待与执行、checkpoint/fsync。复用这些埋点，先核对新PSD调用路径是否实际经过它们。normal保留低成本汇总，debug用于定位，二者配置及观测开销必须列入基线。

当前客户端HTTP埋点不能区分服务端排队、prefill、decode或TTFT；非流式响应头耗时也不是TTFT。有服务端指标时按实例/测量窗口取差分；没有逐请求关联就仅报告聚合，不伪造逐样本拆解。完整窗口验收计算已实现并通过固定镜像7项测试；真实任务边界与后台采集尚未联调，尚无真实利用率通过证据。

### 固定报告表

每轮原位更新：配置hash与资源 → 生成/验收/评分进度 → 供给、推理、验收各自平均/P50/P95与等待 → ready及验收队列 → 逐卡利用率/覆盖 → 吞吐、样本延迟、ETA → 首要瓶颈与下一项配置调整。没有证据的字段写“未测得”，不填0。

优化顺序由瓶颈决定：供给不足先缓存/预载/并行准备；供给充足而推理慢再调并发/批处理及prefix；验收不足先并行校验、复用不变资产核验与异步评分。所有优化保留冻结知识、合法性验证、checkpoint持久性和原始费用。

## 完整窗口验收工具

复用 `scripts/npu/card_utilization_monitor.py`，采集模式不变；新增只读离线验收：

```bash
python scripts/npu/card_utilization_monitor.py \
  --assess-samples samples.jsonl --windows windows.json --out acceptance.json
```

`windows.json` 使用 `schema: saea-utilization-windows-v1`、`threshold_percent: 80`、`max_sample_gap_seconds: 60`，以及 `windows` 数组。每个实例指定唯一 `id`、互不重叠且总计覆盖8卡的 `cards`、带时区的 `first_dispatch` / `last_response` 与 `boundary_evidence_sha256`。边界必须来自完整请求账本，hash只是证据引用，工具自身不证明窗口选择正确。60秒为30秒采样的最大允许间隔配置，实际间隔同时留在原始记录中。

工具要求采样覆盖窗口两端，以相邻观测线性插值得到时间加权均值；这是观测估计，不是连续硬件计量。任一卡缺测、非法读数、超限间隔或未覆盖窗口时返回 `INSUFFICIENT_EVIDENCE`；完整证据下任一卡均值不大于80返回 `FAIL`；仅全部通过返回 `PASS` 和退出码0，其余退出码2。输出保留采样及窗口配置hash，不覆盖已有报告。P10和零利用率比例仍为离散观测统计。

代码 `67a78af5` 已在固定镜像执行7项测试，覆盖逐卡失败、严格阈值、采样断档、缺测、两实例不同窗口和输入身份。该结果只证明验收计算，真实PSD基线仍待启动和测量。
