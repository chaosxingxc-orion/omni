# 轨迹工程与模型错误的边界

依据用户最新澄清：错误归因在证据输入和程序处理正确的前提下，是模型理解/推理问题，不因可增加脚本约束就归为程序bug。

## 工程负责事实可靠与可追溯

固定脚本负责原始响应保全、样本与请求对应、知识来源标记、节点顺序、raw/delivered差分、官方评分、成本、断点、候选版本及评测。输入串样、遗漏关键字段、错计分、错误解析、违反既定语义的交付转换属于程序bug；修复并回归后再评价算法。

脚本化可以保证轨迹结构与证据质量，不能保证每条轨迹答案正确、诊断正确或知识有效。错误轨迹保留作负例；不能因通过格式校验就当作正确示范。

## 模型负责判断与提出改进

在真实证据已正确提供时，模型把检索示例当当前语音、忽略原始回答已有实体、提出不受证据支持的归因、产生与固定上下文冲突的知识或指令，属于模型行为与算法优化问题。提示已明确区分而模型仍混淆，不应继续归为输入程序bug。

`node-grounded-feedback-v2`把可计算节点差分作为更清晰反馈，属于上下文/学习反馈设计。它不会把未知语音变为已知事实，不证明删槽原因，也不能保证模型采用证据。最终通过节点干预、固定真实数据配对评分和repair/break验证假设。

## 已知现象如何处理

| 现象 | 分类和动作 |
|---|---|
| artifact封存回调读错字段 | 程序bug，修协议与回归 |
| 轨迹串样、评分或差分计算错误 | 程序bug，阻止进入学习 |
| 空库模型引用date作为知识ID | 模型输出违约；程序应检测/隔离并留证。若协议定义矛盾，则另有程序契约bug |
| 模型将检索meetings当当前语音 | 模型理解/归因错误；对比反馈设计与学习策略 |
| raw有date、delivered没有 | 可计算事实；先检查交付规则契约，不能仅凭变化认定bug |
| 错误intent使模型删掉正确槽位 | 模型推理问题；交付程序若按错误规则二次删槽，应另查规则语义 |
| time_zone描述与标签不一致 | 知识/数据语义问题，追溯构建来源并做干预；不自动归咎运行代码 |

## 开发优先级

先让轨迹采集、检查、反馈构造、评测和晋升脚本化并锁定功能基线；明确程序缺陷先修。模型失败和负例进入TFRL的反思—候选—真实干预—评分闭环，不由脚本伪造正确轨迹。开发预算按研究需要保留，研发协作tokens单独优化。
